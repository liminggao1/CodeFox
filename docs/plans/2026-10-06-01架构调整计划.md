# agent-harness 架构调整计划

> 2026-10-06 · 状态：已实施。下文保留实施前的依据与步骤；结果见文末执行记录。

## 目标与边界

- 降低定位一次工具调用、任务分配和恢复流程时需要跨越的模块数量。
- 明确可变状态的所有者，消除有实际维护成本的双向依赖。
- 保留现有功能、同步主循环和按机制平铺的源码布局；不以课程数或文件数为目标。
- Lead、队友和子 agent 保持独立循环、独立工具集合与停止条件。它们已经共用基础工具实现和 hook；不把三个循环并成一条主路径。
- `flat/agent_full.py` 保持仓库内可直接运行的生成物。当前没有脱离仓库单独运行的要求。

## 职责目标

| 模块 | 主要责任 | 不再承担的责任 |
| --- | --- | --- |
| `host` | Lead 的 agent 循环、上下文、Stop 边界和运行接线 | 充当所有功能模块的可变状态副本 |
| `tasks` | 任务持久化、认领、assignment 的目录查询与释放 | 通过动态导入直接修改队友协议状态 |
| `task_worktrees`（拟新增） | 任务与 worktree 绑定、解绑的完整操作，包括状态检查、加锁、Git 调用与部分成功后的报错 | 维护独立的任务或 Git 状态副本 |
| `worktrees` | Git worktree 的创建、校验和移除；按 worktree 名称解析目录 | 读取任务、assignment 或后台调度状态 |
| `teams` | 队友循环、邮箱和审批协议；在队友任务入口检查 plan gate、更新审批状态 | 直接改任务存储或让任务模块修改审批状态 |
| `subagent` | 有限轮次的独立子 agent 循环 | 继承 Lead 的 cron、goal、memory 等机制 |
| `workflow` / `scheduler` | 各自的 journal / 调度状态转换 | 把恢复规则分散到调用方 |

`task_worktrees` 不是转发层：它隐藏现有创建和移除流程中的跨模块校验、锁顺序、Git 失败与任务绑定失败处理。其对外接口只有“为任务创建 worktree”和“移除已绑定 worktree”；具体函数名实施时确定。依赖方向为 `teams` / `file_tools` -> `tasks` -> `worktrees`，`task_worktrees` -> `tasks` / `worktrees` / `scheduler`；`worktrees` 不反向导入任务。保留现有工具返回文本，避免调用方学习新的错误协议；不新增通用依赖注入框架。

## 执行顺序

### 1A. 修复 assignment 目录查询（最高优先级）

1. 先补一个能复现 `assignment_cwd()` 错误的回归测试，覆盖普通任务和绑定 worktree 的任务。
2. 只修正错误调用，并固定“完成后到回合结束仍可使用目录”的现有行为；此步不搬迁模块。

**完成条件：** 普通任务和绑定任务的目录查询均通过测试，错误绑定仍被拒绝。

### 1B. 收拢任务生命周期与 Git 绑定（高优先级）

1. 记录认领、完成、回合结束释放、队友线程退出，以及创建、移除 worktree 的状态转换和调用者；确认 `host`、`teams`、`file_tools`、`registrations`、`mcp_tools` 与离线自检的入口。
2. 将 assignment 的查询和释放移到 `tasks`；`teams` 在队友入口负责 plan gate 检查，并在 assignment 版本变化后使旧审批失效。`tasks` 不再导入 `teams` 或读取其全局字典；Lead 的任务完成不受队友审批规则影响。
3. 将 Git 路径解析改为只接收 worktree 名称，不接收 `Task`；让任务可认领检查和目录解析通过 `tasks` 的接口完成。`teams` 不再同时读取任务内部字典与 worktree 注册信息。
4. 将创建并绑定、校验并移除的完整操作移到 `task_worktrees`；调用方只使用这两个接口。任务检查到绑定写入期间持有 `tasks.task_store_lock()`；移除时在检查任务状态、目录租用和当前进程后台命令后，维持相应锁直到 Git 移除完成。明确任务锁先于后台命令锁，避免反向持锁调用。
5. 保留 Git 操作成功但任务写入失败时“不删除 Git 数据、返回部分成功信息”的现有处理；不承诺跨进程后台命令可见性。

**完成条件：** `tasks` 与 `worktrees` 无双向导入，`worktrees` 不读写任务或调度状态；从认领入口能找到唯一的 assignment 状态路径；普通任务、绑定任务、异常退出、跨进程认领与绑定竞争、移除时仍在用的目录均有行为测试。

### 2. 会话运行状态（高优先级）

1. 以现有 `core` 为启动目录、client、CLI 状态和模型配置的唯一所有者；先修正 `cli` 写入 `core.CLI_ACTIVE`。`workflow.RUNNER_FACTORY` 是真实运行与离线测试使用的不同实现，保留这个替换点。
2. 逐项清点 `core.TRANSCRIPT_DIR`、`core.TOOL_RESULTS_DIR`、memory 的目录与索引、workflow 的 `STORE` 等派生路径；使它们从当前启动目录取得，不靠重复同步各模块的全局路径。
3. 移除 `host.client` 可写副本和不起作用的“实时视图”接线，让使用方读同一份 client。只保留确有调用方需要的 `host` 导出；同步调整 CLI、测试和 flat 构建，不增加通用会话类。

**完成条件：** 切换测试启动目录后，任务、transcript、tool result、memory、workflow 和调度文件都写入新目录；CLI 输出状态和 client 替换由同一所有者生效；无需在测试夹具中逐模块同步路径。

### 3. 恢复与持久化语义（中优先级，两项可独立做）

**workflow journal：** 默认保留现有“相同 `prompt/label/schema` 共用一次结果”的语义；若业务确需两次独立执行，再单独设计调用身份，不能依赖并行完成顺序。journal 记录可恢复的历史 token 用量；run 总预算包含历史用量，但缓存回放本身不产生新 token。先判定回放，再对新模型调用检查剩余额度；返回后核算实际用量，超额时按现有规则报错。区分本次 resume 新增用量与整个 run 累计用量，防止同一缓存键重复计费。实施前确认现存 journal 是否需要继续恢复，并补重复调用、部分完成后 resume、恰好用满预算后纯回放的测试。

**scheduler：** 默认保留循环 cron 仅在当前进程内按分钟去重；同一分钟重启后可再次触发，不承诺严格只执行一次。持久化的一次性任务采用至少一次交付：入队前落盘，模型调用被接受后才确认；确认前崩溃允许重投。对新建、取消、入队、确认四种写盘失败，先保留或恢复内存中的未提交状态，使它与磁盘一致，再返回错误；补重启与各写盘失败测试。不扩展为跨进程调度协调。

**完成条件：** journal 能解释每次调用是新执行还是回放；纯回放不因历史预算用满而失败，预算已用尽时不再发起新调用，实际用量超额时返回预算错误；cron 重启与持久化失败的交付规则均有对应测试。

### 4. 工具路径（保留独立，按证据决定是否抽取）

Lead 负责 cron、压缩、goal 和后台通知；队友负责邮箱、任务与 plan gate；子 agent 只运行有限轮次和受限工具集合。这三种循环继续分开。共享范围限于已有的文件工具实现、handler 调用和 hook 规则。只有发现三处确实重复维护同一条规则并导致行为分叉时，才抽取小的执行函数；不创建统一的 agent 主循环。

**完成条件：** Lead、队友、子 agent 的工具权限和结果行为各有测试；阅读任意一种循环时无需进入另外两种循环才能理解它。没有可证实的分叉则此阶段只保留设计约束，不改代码。

### 5. flat 与调试文档（文档纠错可提前）

`flat` 按“在本仓库内，一个脚本即可作为入口运行”维护。保留当前生成机制；只有确认 CLI 两份入口已经产生行为差异时才消除重复。[GLOSSARY.md](../../GLOSSARY.md) 中“拼四个模块”的旧描述与 [dev-notes.md](../../note/dev-notes.md) 中已不适用的路径常量说明会误导调试，可作为独立文档改动提前修正。调试入口继续指向 `src/codefox/`。

**完成条件：** README、术语表和调试笔记对 `flat` 的能力描述一致；生成物仍由脚本生成，源码变动后生成物新鲜度检查通过。

## 实施与验证约束

- 每一阶段单独改动和验证，不把全部候选合成一次大重构。先做 1A 再做 1B；第 2 阶段可独立于第 3 阶段，workflow 与 scheduler 也可分别处理。文档纠错无需等到最后。
- 每个阶段先运行最贴近改动的现有测试，再补必要的行为用例。源码改动后重建 `flat`，运行完整 `pytest -q` 和 `scripts/debug_pass.py`；环境与命令以 [AGENTS.md](../../AGENTS.md) 为准。
- 不直接修改 `flat/agent_full.py`。保留真实 Git worktree、子进程 CLI 与 flat 的离线自检。
- 完成一阶段后再更新对应文档中的“已实现”描述；本计划中的目标和完成条件在验证前都不视为现状。

## 执行记录

- 1A：`assignment_cwd()` 的错误调用已修复；普通、有效绑定和失效绑定均有测试。
- 1B：`tasks` 管理 assignment，`worktrees` 只管 Git 与目录，`task_worktrees` 管理绑定和移除。创建与移除持有跨进程任务锁；后台命令登记与移除使用任务锁先于后台锁。队友审批在 `teams` 入口检查，Lead 完成任务不受队友审批影响。
- 2：启动目录、client、CLI 状态统一由 `core` 持有。任务、memory、workflow、transcript、工具结果和提示词在调用时读取当前目录；`host` 不再维护 client 副本。
- 3：journal 记录每次新调用及累计 token 用量，相同键的并发调用只执行一次。旧格式记录缺少 `tokens` 时 resume 明确报错；原有文件保留，重新运行可生成新格式。持久化的一次性任务写盘失败会回滚内存状态；确认失败时重新入队。循环 cron 仍只在本进程去重。
- 4：保留 Lead、队友和子 agent 的独立循环；现有底层工具与 hook 共用已足够，未新增统一主循环。
- 5：flat 仍是仓库内单文件入口；更新生成顺序和 README、术语表、调试笔记中的职责与运行范围。

验证：`python -m pytest -q` 共 123 项，`scripts/debug_pass.py` 共 9 项；`flat/agent_full.py` 已由 `scripts/build_flat.py` 重新生成。
