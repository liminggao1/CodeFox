## 目标

在保留现有行为的前提下，把浅的 module 加深：

- 让 memory 的 interface 只表达记忆能力，删除不会被调用的旧 Agent runtime。
- 让运行时上下文有明确的所有者和 seam，消除未使用参数与共享 dict 的隐式约定。
- 让队友协议和队友执行循环分开，给测试一个可替换的 adapter seam。
- 让 workflow runtime 与示例编排分开，缩小核心 module 的 interface。
- 让内置工具、MCP 工具、handler 和权限策略在一个装配 seam 汇合，解除循环依赖。
- 最后再评估 host facade 的重导出范围，避免在前几个阶段同时迁移大量调用方。

## 约束与非目标

- 保留 Lead、队友和 subagent 的独立循环，不做统一 Agent loop 重构。
- 保留同步主循环，不引入异步化重构或通用依赖注入框架。
- 保留现有工具名称、工具结果文本、goal Stop 语义、任务和 workflow resume 语义。
- `flat/agent_full.py` 继续由 `scripts/build_flat.py` 生成，不直接编辑。
- 不新增第三方依赖；所有测试继续在 WSL 的 `learncc` 环境离线运行。
- 每个阶段独立提交、独立验证；阶段未通过时停止推进后续阶段。

## 执行规格和阶段门

本计划按“一个阶段、一个可回退提交、一个验收门”执行，不把所有阶段合并成一次大重构。每个阶段开始前必须补齐或确认以下四项：

1. **目标文件**：列出新增、修改和删除的源码、测试、脚本与文档文件。
2. **接口决策**：写出 seam 的输入、输出、状态所有者和调用方；未决的方案不能直接进入实现。
3. **迁移顺序**：先增加或移动实现，再迁移调用方，最后删除旧入口；每一步都能运行相关测试。
4. **验收证据**：记录测试命令、结果、`git diff --check`、flat 新鲜度和行为保持结论。

阶段门只有在源码、测试和生成物都通过后才能关闭。基线、引用清单和阶段验收结果统一记录在本计划的“实施记录”中。

## 阶段 2：建立 RuntimeContext seam

### 现状证据

- `host.update_context(context, messages)` 的 `context` 输入当前没有被读取。
- `agent_loop` 内部重新绑定局部 `context`。
- `async_event_loop` 结束后再用 `context.update(...)` 修补共享 dict。
- `prompts.assemble_system_prompt` 通过未类型化字符串 key 读取上下文。

### 实施步骤

1. 盘点 context 的字段：memory catalog、相关记忆、connected MCP、active teammates，以及 prompt 真正消费的字段。
2. 设计一个小的 RuntimeContext seam 或 ContextBuilder seam，集中负责快照构造；先不扩大字段范围。
3. 明确快照的所有者：构造方负责刷新，prompt 只读，Agent loop 不再通过隐式 dict 重绑状态。
4. 删除 `update_context` 和未使用的上一快照参数；同步修改 CLI、后台事件循环和测试夹具。
5. 让 `agent_loop` 使用同一份刷新后的上下文组装系统提示词，并保留动态 MCP、队友和 memory 状态刷新时机。

### 执行时采用的接口

- 新增 `src/codefox/runtime_context.py`，定义只读的 `RuntimeContext` 数据对象，字段固定为 `memory_catalog`、`memories`、`connected_mcp` 和 `active_teammates`。
- `runtime_context.build_context(messages) -> RuntimeContext` 是唯一的快照构造入口；它读取 memory、MCP 和队友状态，但不修改这些模块的全局状态。
- `RuntimeContext.prompt_values() -> dict` 只在 prompt 边界把快照转换为现有 key，`prompts.assemble_system_prompt` 不直接读取运行时全局对象。
- `agent_loop(messages, active_request)` 在每次模型调用前构造快照；CLI 和后台线程只传递历史与当前请求，不保存上下文副本。
- 删除 `host.update_context`，调用统一改为 `build_context(messages)`，不再通过 `context.update(...)` 修改共享对象。

### 迁移顺序

1. 先新增 `RuntimeContext` 和快照测试，保留旧 `update_context` 作为内部调用点。
2. 迁移 prompt、host 和 CLI 的调用方，验证字段内容与提示词文本不变。
3. 迁移后台事件循环，删除共享字典的原地更新。
4. 所有调用方迁移后再删除旧入口，并更新 flat 构建顺序。

### 测试与完成条件

- 保留现有 prompt、goal、scheduler 和 agent loop 行为测试。
- 增加 context 快照测试：MCP 连接、队友状态、memory 变化能在下一次模型调用中出现。
- 增加所有权测试：后台事件循环不会覆盖调用方仍在使用的旧快照。
- 不再需要通过 `context.update` 修补共享 dict；所有 context 字段有唯一构造路径。

### 风险与回退

这是对 host、cli、prompts 和测试调用方式的联动改动。先只改变 context 的构造与传递，不改变字段内容和模型提示词文本；若行为失败，回退本阶段提交即可。

## 阶段 3：统一 ToolRegistry / MCP 装配 seam

### 现状证据

- `registrations.py` 顶层导入 `mcp_tools`，提供 `run_connect_mcp`。
- `mcp_tools.assemble_tool_pool` 又延迟导入 `registrations`，形成反向了解的循环依赖。
- 内置 schema、handler、MCP 动态工具和权限策略分布在 `registrations.py`、`mcp_tools.py`、`hooks.py` 三处。

### 实施步骤

1. 先固定当前工具池顺序、名称冲突、默认 `confirm`、MCP 连接后刷新和 handler 闭包行为。
2. 抽出一个只负责工具目录与装配的 module 或内部 adapter seam；具体名称和 interface 在实施前根据两种方案比较后确定。
3. 让内置工具目录提供 schema 与 handler，MCP adapter 提供动态工具与来源信息，装配 seam 统一生成工具列表、handler 映射和 policy snapshot。
4. 移除 `registrations` 与 `mcp_tools` 的循环 import，避免通过局部 import 隐藏依赖方向。
5. 保留 `host` 必要的兼容导出，暂不在本阶段同时迁移所有测试和调试脚本。

### 执行时采用的接口

- 新增 `src/codefox/tools/tool_registry.py`，定义 `ToolSnapshot` 和 `ToolRegistry`。
- `ToolRegistry.snapshot() -> ToolSnapshot` 是唯一的工具池读取入口；快照包含模型可见的 `tools`、名称到 handler 的映射，以及规范化后的 policy。
- `registrations.py` 只提供内置工具目录和 handler；`mcp_tools.py` 只负责 MCP 连接、动态工具发现和 MCP handler adapter；policy 由 registry 组合，不由 host 重新拼接。
- registry 不导入 `registrations` 或其他来源；来源仅引用其 `ToolDefinition` interface，不访问 registry 实例。内置目录通过显式接线传入，禁止用局部 import 隐藏依赖方向。
- 保留 `assemble_tool_pool()` 作为短期 facade，但其实现只能委托给 `ToolRegistry.snapshot()`，不得保留第二套装配逻辑。

### 迁移顺序

1. 先为现有工具池记录顺序、重名处理、权限和 handler 异常文本。
2. 新增 registry 和快照测试，让旧 `assemble_tool_pool()` 委托 registry。
3. 迁移 host、CLI 和测试读取快照，验证 MCP 连接后的下一轮刷新。
4. 删除 `registrations` 与 `mcp_tools` 的反向导入，再移除 facade 内的重复代码。

### 测试与完成条件

- 保留并扩展工具池测试：内置工具、Workflow、MCP 动态工具、规范化冲突、64 字符限制和默认权限。
- 增加装配快照测试，确认连接新 MCP 后下一轮能看到新工具。
- 增加循环依赖检查或最小导入测试。
- 新增工具只需在其目录和 handler 位置维护一次，权限策略不会分散到调用方。

### 风险与回退

工具名称和权限是模型可见行为，任何变化都可能破坏调用流程。先用现有测试锁定输出，再迁移实现；保持旧的工具返回文本和 handler 异常文本。

## 阶段 4：抽出 TeammateSession adapter

### 现状证据

`teams.spawn_teammate_thread` 的大闭包同时处理 mailbox 协议、assignment、plan gate、线程生命周期、模型循环、工具 schema 和多个 cwd wrapper。测试还直接依赖私有 `_run_teammate_tool`，执行 seam 对实现细节耦合较强。

### 实施步骤

1. 先画出队友一次任务的状态转换：spawn、claim、plan approval、working、idle、shutdown、release。
2. 把协议和状态所有权留在 `teams`，把一次队友执行所需的 owner、assignment、cwd、client、工具集合和 hooks 收拢到 TeammateSession adapter 的内部 seam。
3. 让队友线程只负责生命周期和事件投递；执行细节由 adapter 负责，保留 Lead、队友、subagent 的不同工具权限和停止条件。
4. 将 `_run_teammate_tool` 的实现耦合测试改为 adapter 行为测试，使用 fake client 或 fake handler 验证工具结果和 plan gate。
5. 保留 mailbox request id、旧计划响应失效、shutdown 审批和任务释放语义。

### 执行时采用的接口

- 新增 `src/codefox/teammate_session.py`，定义内部 `TeammateSession` adapter。
- adapter 接收名字、LLM client、模型、系统提示词与授权、发消息、提交计划的回调；每次工具调用从 tasks 查询当前 assignment/cwd，避免领取新任务后使用旧目录。
- adapter 提供 `run(messages) -> response`（一次模型与工具轮）和 `execute_tool(block) -> str`；线程生命周期、等待、消息接收和状态更新仍由 `teams.py` 负责。
- `teams.py` 保留协议函数和状态所有权，只把模型循环与工具执行委托给 adapter；不得把 Lead 的 context、cron、goal 或 memory 传入 adapter。

### 状态迁移顺序

按 `spawn -> claim -> plan approval -> working -> idle -> shutdown -> release` 顺序迁移，每次只迁移一条状态路径。每条路径都要验证 request id、assignment version 和异常退出后的 release，确认通过后再迁移下一条路径。

### 测试与完成条件

- 保留现有 plan approval、shutdown、assignment 版本和 mailbox 协议测试。
- 增加 fake client 下的队友工具循环测试，不依赖真实线程等待。
- 增加异常退出和任务完成后的 assignment release 测试。
- `teams` 不再需要理解 Lead 的 context、cron、goal 或 memory；队友工具行为仍与现状一致。

### 风险与回退

并发和审批状态是主要风险。先只抽取内部 adapter，不改变 mailbox 格式和全局状态名称；每次只迁移一条状态路径并运行团队测试。

## 阶段 6：评估并收窄 host facade

### 现状证据

`host.py` 既承载 Lead agent loop，又重导出 tasks、teams、hooks、scheduler、MCP、file tools、workflow 等大量名称。CLI、测试和 debug 脚本广泛通过 host facade 使用，因此它是现有真实 seam，不能直接一次删除。

### 实施步骤

1. 在阶段 2-5 完成后重新统计 host 外部使用的名称，区分真实兼容入口和仅为历史方便保留的导出。
2. 对每个候选导出应用删除测试：删除后是否能让复杂度集中到真实 module，还是只把复杂度扩散到所有调用方。
3. 先迁移内部代码和新测试直接导入真实 module，再保留必要的 host facade 兼容导出。
4. 只有在调用方迁移成本可控且 interface 更深时，才删除历史导出；不要为了减少行数而制造新适配层。
5. 更新 README、GLOSSARY、debug 文档和 flat build 说明。

### 测试与完成条件

- CLI、debug_pass、完整测试和 flat build 全部通过。
- host 仍只负责 Lead 主循环、上下文、Stop 边界和接线，不再成为可变状态副本。
- 每个被移除的导出都有明确迁移位置和测试覆盖。

### 风险与回退

这是最后阶段，因为它可能触及最多调用方。若删除 facade 不能带来更高 depth，保留 facade 并记录为稳定兼容 seam，不为形式上的收窄继续重构。
