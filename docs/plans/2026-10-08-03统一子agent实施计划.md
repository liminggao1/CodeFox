## 目标与已确定的决策

统一“一次性子代理”和“持久队友”，对用户及模型统一称为**子 agent**。
模型使用一个创建工具，通过运行模式决定实例完成当前委派后结束，还是等待后续工作并保留上下文。
`once` 可以执行多次模型请求和工具调用；`persistent` 的持续存在仅限当前进程，不包括退出程序后恢复实例。

1. 新工具名为 `spawn_subagent`，替换 `task` 和 `spawn_teammate`，不保留工具别名。
2. `mode` 由 Lead 模型选择，必须显式传入 `once` 或 `persistent`。运行时不猜测模式。
3. 用户明确指定模式、并发方式或禁止委派时，模型遵守用户要求；没有指定时根据任务选择。
4. 模式选择及创建不新增用户确认步骤。修改现有提示词中“先提议团队并等待用户确认”的规则，使其与本次授权一致；已有 shell 权限 hooks 和显式计划审批仍按其职责执行。
5. 合并共享模型回合、工具执行、工具定义和任务目录处理，保留两种生命周期。不能只增加一个分发包装器后保留两套重复的执行实现。
6. 本次沿用现有执行方式：`once` 在工具调用内同步等待结果；`persistent` 启动工作线程后立即返回，由运行时交付后续事件。这是执行方式的选择，不是一次性生命周期必须同步；本计划不新增异步 once 模式。
7. 本次在创建时选择模式，实例存活期间模式固定。已结束的一次性实例不会自动恢复；需要保留上下文并连续接任务时，创建时选择 `persistent`。
8. 此计划替代前两轮架构计划中“保留分开的 subagent / 队友循环及旧工具名”的相关约束，并以本文明确的新行为为准；其他已实施行为继续保留。
9. 主动通信由发送方模型决定，包括是否需要通信、发送时机、接收者和内容。运行时负责投递、唤醒和状态通知，不根据任务关键词自行生成协作消息。
10. 是否使用任务板与运行模式分开。两种模式有有效任务分配时使用任务目录，没有分配时使用启动目录；已有分配失效时返回错误，不能退回启动目录。
11. 移除空闲线程定时扫描并自动认领第一个任务的行为。初始认领由 Lead 显式传入 `task_id` 触发；后续认领由子模型调用 `claim_task` 触发，运行时只校验和执行。

## 对模型的 interface

### 创建工具

```text
spawn_subagent(name, prompt, mode, role="coder", task_id=None, require_plan=False, tools=None)
```

| 参数 | 规则 |
| --- | --- |
| `name` | 必填，两种模式使用同一名称规则；不得与仍活跃的实例重名，保留 `lead` / `agent` 名称 |
| `prompt` | 必填，非空任务指令；替换旧 `task.description` 与 `spawn_teammate.prompt` 的两套表达 |
| `mode` | 必填，枚举 `once` / `persistent`；缺失或非法值在登记和请求模型前拒绝 |
| `role` | 可选，默认 `coder`，进入子 agent 的系统提示词 |
| `task_id` | 可选；指定时，两种模式均在执行模型前认领对应任务，采用其有效工作目录 |
| `require_plan` | 默认 False；只允许 `persistent` 使用 True，避免同步子 agent 等待被阻塞的 Lead 审批 |
| `tools` | 可选工具白名单；省略为模式默认工具，`[]` 关闭工具；不能扩大模式能力 |

schema 使用 `additionalProperties: false`。名称、模式、任务认领与模式相关组合也在 Python interface 内验证，不能只依赖 schema。

模型选择原则写入提示词：任务范围明确、只需最终结论时选 `once`；需要连续任务、往返消息或计划审批时选 `persistent`。
这些是模型决策依据，不是程序按关键词或阈值强制选模式的规则。

创建工具统一返回 JSON 文本，由 registrations 负责序列化，字段为：

```json
{"name": "auth", "mode": "once", "status": "completed", "text": "任务结果", "usage": {"tokens": 100, "model_calls": 1}}
```

- `once` 等待执行结束，返回 `completed` 及总结；模型异常、截断或达到轮数上限仍未完成时返回 `failed` 及原因。
- `persistent` 完成登记和线程启动后返回 `started`；它表示启动被接受，不能解释为任务已完成。结果和错误随后通过既有信箱事件交付。
- 校验或线程启动失败返回 `failed`，不得留下活跃登记、任务分配或计划门禁。
- 名称和模式校验成功后返回两者；校验失败时，仅回填已验证的值，其余字段为 null，`text` 明确指出失败原因。缺失必填参数由工具分发层拒绝，不进入创建函数。

### 管理工具

| 工具 | 统一后的行为 |
| --- | --- |
| `list_subagents` | 替换 `list_teammates`，列出活跃实例的名称、模式、角色和状态 |
| `send_message` | 保留 `to` / `content` 参数；Lead 发给活跃持久子 agent，持久子 agent 可发给 `lead` 或其他活跃持久实例；一次性实例不接收后续信箱工作 |
| `request_shutdown` | 名称保留，目标参数统一为 `name`，只关闭持久实例 |
| `request_plan` | 名称保留，目标参数由 `teammate` 改为 `name`，正文参数 `task` 保留 |
| `review_plan` | 保留 `request_id` / `approve` / `feedback`，由请求 ID 定位实例，不新增名称参数；继续校验当前任务、分配版本与计划请求 |
| `remove_worktree` | 继续只供 Lead 请求；保留已实现的成功后释放自身分配规则 |

不能给任一子 agent 提供 `spawn_subagent`、依赖修改或 worktree 创建/移除工具，保持不可递归和 Lead 的协调职责。
不存在针对已结束一次性实例的消息、关闭或模式升级入口；这些请求返回明确的不存在或模式不适用错误。

### 主 agent 与子 agent 的通信

Lead 和持久子 agent 都可以由各自模型调用 `send_message`。模型判断是否需要澄清、汇报进展或请求协助，也可以不发送中间消息；不要求每轮发信或固定频率汇报。子 agent 发送给 `lead`，Lead 发送给目标子 agent 的名称，持久子 agent 之间也沿用该入口。

一次性模式通过创建工具的最终返回值向 Lead 交付结果，不提供往返信箱。Lead 判断需要执行期间的双向交流时，应在创建时选择 `persistent`。运行时不因消息内容自动切换模式。

执行结果、失败、IDLE 和关闭确认仍由运行时按现有协议通知，保证 Lead 能知道执行状态。这些状态通知不属于模型自行决定是否发送的中间协作消息；无需新增“是否通信”参数或独立决策模型。

### 后续任务与空闲等待

- 不使用任务板：Lead 通过 `send_message(to=name, content=工作说明)` 发出下一次委派；子模型处理后汇报，实例继续等待。单纯调查不要求创建 Task。
- 使用任务板：Lead 创建任务并按需绑定 worktree，等待目标子 agent 的 IDLE 通知后，发送任务 ID 和工作说明；子模型先调用 `claim_task(task_id)`，成功后执行任务目录中的工作。
- 子模型可以根据当前委派调用 `list_tasks` 决定是否认领其他任务；成功认领才能切换任务目录。每个实例同时最多占用一个任务，不创建由程序选择任务的定时轮询。
- 收到消息会唤醒持久实例，但不等于认领任务。WORK 期间的消息可以提供澄清或协调信息，不能直接覆盖当前分配；新任务的认领仍受占用和依赖检查约束。
- IDLE 只等待消息或关闭请求；任务板出现新任务本身不会让线程自动认领，也不会无消息地请求模型。是否派活、查看任务板或停止实例由模型通过已有工具决定。

## 工具能力与目录规则

| 能力 | `once` | `persistent` |
| --- | --- | --- |
| bash、读、写、编辑、glob | 共享同一套定义和实现 | 共享同一套定义和实现 |
| 任务认领、完成及任务列表 | 指定 `task_id` 时提供；无任务的临时查询不提供任务管理工具 | 提供，由模型显式认领；空闲运行时不认领 |
| 消息与提交计划 | 不提供 | 提供 `send_message` / `submit_plan` |
| 当前任务完成后 | 汇报并结束实例 | 汇报后进入 IDLE，保留上下文 |
| 工作目录 | 有有效分配时使用任务目录；没有分配时使用启动目录；分配失效时报错 | 同 once，不因持久模式强制使用任务板 |

统一名称不表示两种模式必须暴露完全相同的工具。共同能力由同一处构造，持久模式追加需要长生命周期的协作能力。
模型需要“队友的全部功能”时选择 `persistent`，用户不必再理解另一种 agent 类型。

所有工具都复用已有 PreToolUse / PostToolUse hooks，不建立新的权限系统。
工作目录按调用时的任务分配读取，不在创建时复制一份目录归属状态。
任务状态和目录租约继续只由 tasks 管理；信箱和子 agent module 不另存一份任务状态。

## module 与状态所有权

### `subagent.py`：统一创建和生命周期

- 对调用方提供 `spawn_subagent`、查询、发信、关闭、计划操作和事件领取。
- 内部登记使用 `active_subagents`，每条记录含名称、角色、模式、状态、该实例的消息历史和当前委派正文 `active_request`。
- 两种模式均登记后再执行；一次性实例结束或失败后移除记录，持久实例在 IDLE 保留记录与历史。
- 当前 teams 的 MessageBus、pending_requests、计划门禁和协议校验迁入此 module；既有 mailbox 目录、消息类型和 request ID 规则保留。
- 使用一个内部工作回合执行函数循环调用共享 session。持久模式在每次模型请求前处理信箱；一次性模式检查轮数上限。
- 一次性委派结束后执行清理；持久外层继续等待消息或关闭，下一次工作由模型选择工具。不能复制一套“请求模型 → 工具分发 → 回填历史”的第二循环。

继续使用现有模块函数和少量数据记录，不引入通用 actor 框架、插件体系或第二套 scheduler。

### `subagent_session.py`：共享模型回合

- 从现有 TeammateSession 正向修改并改名为 `SubagentSession`；不保留旧类别名。
- 核心 interface 仍是 `run(messages)`，负责一个模型响应及其配对的工具结果。
- 复用现有 client/model/system 依赖和可替换客户端 seam，测试不启动真实模型。
- workspace 工具包装及基础 schema 在此处统一构造，通过实例身份和已确定的模式应用上表的目录规则。
- 持久协作工具通过运行时提供的回调接入；session 不拥有信箱、活跃登记或线程生命周期。
- 截断响应在追加历史和执行工具前拒绝，两种模式统一；不把旧一次性路径的截断结果当作成功总结。

### 上下文增长与压缩

复用 [compaction.py](../../../src/codefox/context/compaction.py) 的 `prepare_history` 与 `reactive_compact`，两种模式采用同一处模型调用前处理。压缩可以用摘要替代旧消息，保留实例身份和历史列表对象，并不要求所有原始消息永远放进模型上下文。

运行时维护当前委派正文 `active_request`；初始 prompt 或从 IDLE 收到新工作消息时更新，WORK 期间的协调消息追加到当前历史，不覆盖委派正文。当前任务 ID、目录和审批状态仍从 tasks 与协议状态读取。压缩后的模型输入必须包含当前委派、当前有效任务及必要的近期消息，不得恢复已结束任务的旧指令。信箱尚未消费的消息独立保留，压缩不读取消费它们。

阶段 1 先将 compaction 的内容 helper 导入迁到 `message_content`，再接入共享 session，避免 `subagent → session → compaction → subagent` 循环。沿用现有预算，主动压缩失败时保留原历史并记录原因。模型明确报上下文过长时，每次委派最多尝试一次被动压缩后重试；再次超限或被动压缩失败则走统一异常清理，不增加新的重试策略。

### 内容 helper 与依赖方向

`extract_text` / `has_tool_use` 当前还被 Lead、compaction 等调用。
将它们迁入小型 `message_content.py`，使普通内容读取不必导入完整子 agent 生命周期。
只迁移实际共享 helper，不增加新的消息对象体系。

```text
core / tasks / file_tools / hooks / message_content / compaction
                      ↓
              subagent_session
                      ↓
                  subagent
                      ↓
      registrations / runtime_context / host
```

compaction 只从 message_content 读取共享内容 helper，不导入 subagent。session 不导入 registrations、host 或 subagent；由统一运行时把所需协议回调交给 session，并使用同一客户端 seam 验证模型调用和摘要路径。
`tasks.assignments` 是 Lead 和全部子 agent 的唯一目录分配表，值及持久化任务格式不变。
任务 owner、`.tasks`、`.mailboxes`、`.worktrees` 等存储不改格式，不添加迁移或兼容读取。

## 状态转换与清理时机

```text
once:
  校验/可选认领 → WORK → 完成或失败 → 释放分配、移除实例 → 返回 Lead

persistent:
  校验/可选认领 → WORK → 汇报 → IDLE → 新消息 → WORK
                               └→ 关闭请求 → 停止并清理实例
```

- 一次模型回合是一次 `session.run(messages)`；一次委派可以含多个模型回合，以模型给出无工具请求的最终回答结束。计划待审批时进入等待状态，不能当作委派完成。
- `complete_task` 只标记任务完成，当前批次和后续模型回合的工具仍使用原任务目录。
- 最终回答交付后释放已完成任务的 assignment。释放不删除 worktree、不清空持久历史，也不停止持久实例；该实例进入 IDLE，下一次认领使用新任务目录。单次 session.run 或工具批次结束都不能提前释放。
- 一次性模式成功结束但任务仍为 `in_progress` 时，不能替模型宣称任务已完成。将返回状态记为 `failed`，说明任务未完成，并释放归属回 pending。
- 一次性模式没有绑定任务时，以正常结束的模型响应判定本次调用完成。
- 持久模式异常或线程退出时，复用现有释放行为：未完成任务回 pending，已完成任务保留结果和 worktree，清除活跃登记和协议索引。
- 有任务的持久实例只有完成并释放本任务，才进入可认领下一任务的状态；不要把未完成任务的正常文本回答误写为“任务已完成”。
- 持久实例给出最终文本但任务仍为 `in_progress` 时，交付结果注明任务未完成，保留任务分配并等待后续指导；禁止认领下一任务。关闭或异常退出时再释放未完成归属回 pending。
- 一次性轮数上限沿用 `core.SUBAGENT_MAX_ROUNDS`，只约束该模式；持久模式不因连续工具轮数达到此值而停止。
- `remove_worktree` 仍需任务完成、没有其他执行者占用、没有后台命令、工作目录干净；新 `assignments` 名称迁移后保留全部清理测试。

## 工作流接入统一子 agent（阶段 4–6，已实施）

### 目标与职责

主模型调用 `spawn_subagent` 与工作流脚本调用 `ctx.agent`，最终使用同一个子 agent 创建和执行入口。
工作流步骤固定使用 `once`：一次步骤允许多个模型回合及工具调用，最终回答后清理实例。
`Workflow` 仍是模型启动整个已登记流程的工具，`ctx.agent` 仍是 Python 编排 interface。
本扩展覆盖此前保留独立 workflow runner 执行路径的约束，不改 Lead 或 goal evaluator。

| module | 负责内容 |
| --- | --- |
| `subagent` / `subagent_session` | 实例校验与登记、工具选择、模型回合、历史压缩、实际模型用量和退出清理 |
| `workflow_runtime` | 步骤顺序、并发限制、预算、JSON 解析与 schema 校验、一次格式重试、journal 与恢复 |
| `workflow_demo` | 已登记审查流程及离线演示输入；演示也经过统一执行入口 |

不新增另一种 agent 类型，不复制模型循环，不调用 Lead 的 JSON 工具处理器绕行。
生产代码中 workflow 不再直接请求模型；测试通过统一入口使用的 fake client 保持离线。

### 接口与行为决策

1. `spawn_subagent` 增加可选 `tools` 白名单；省略为当前模式原有工具池，`[]` 明确表示无工具。
   模型工具 schema 同步增加该参数。白名单从 session 已有工具定义中选择，不能扩大模式原有能力；未知名称或非法输入在登记、认领和模型请求前返回失败。
2. Python 创建 interface 增加仅限关键字的 `client`、`model`、`max_tokens` 注入参数，默认沿用 core 配置；这些依赖不进入模型工具 schema。
   session 的执行请求采用给定输出上限，压缩摘要仍采用现有摘要上限；两个路径使用同一注入客户端和模型。
3. `ctx.agent(prompt, schema=None, label=None, phase=None, *, tools=None)` 增加步骤工具配置。
   按用户选择，工作流省略 tools 或传入 None 时默认开放 `bash/read_file/write_file/edit_file/glob`；`[]` 明确关闭工具，非空列表限制为所列基础工具。
   工作流本轮不接受 Task 绑定、持久模式、通信或计划审批。文件工具采用启动目录及现有 hooks，不改变进程全局 cwd。
4. workflow 的执行 adapter 调用 `spawn_subagent(mode="once", role="workflow", tools=...)`，传入客户端、模型和 `core.WORKFLOW_AGENT_MAX_TOKENS`。
   使用 `wf-` 加 UUID 十六进制值生成合法内部名称，label 保留用于 journal 和进度展示，不能直接拿含冒号或中文的 label 当实例名。
5. 创建结果保留 `name/mode/status/text`，新增 `usage={"tokens": 0, "model_calls": 0}`。
   once 的 usage 累计本次所有执行和摘要请求中实际响应的输入、输出 token；截断、无效结果或失败前已发生的消费也计入。
   model_calls 记录实际发出的请求数，包括无响应的异常请求；tokens 只累加收到的用量，不估算真实 API token。
   persistent 的 started 返回零快照，后续实际用量仍由存活实例维护；本扩展不新增持久用量查询工具。
6. 共享执行根据最终工具列表生成能力说明。无工具的工作流步骤仅使用传入文本；显式开放工具后使用同一个工具执行、权限和截断检查路径。
   `SubagentSession` 拥有唯一模型回合实现；workflow adapter 仅转换结构化请求、结果和错误，不维护另一套模型循环。
7. 保留 `RunnerOutput(value, tokens)` 作为 workflow 内部结果。原 `AnthropicAgentRunner` 替换为调用统一入口的 `SubagentRunner`，不保留旧类别名。
   adapter interface 为 `run(prompt, schema=None, label=None, *, tools=None)`，输出仍是 RunnerOutput；工具配置传到统一入口，不存一份独立工具定义。
   原 mock runner 的直接返回路径改为 fake client：生成与模型响应相同的 content/usage，由真实 session 解析和执行。离线 demo 不请求网络。
8. schema 提示和 JSON 解析仍由 workflow 负责。格式无效时最多再调用一次统一 once 入口，保持现有格式重试上限。
   格式重试输入包含上次最终结果、schema 与校验错误，只修正结果格式，固定 `tools=[]`，不能重新执行原步骤的文件或 shell 操作。
   创建失败、轮数耗尽、截断或执行异常是执行失败，不触发格式重试；adapter 抛出带已消费 tokens 的 `WorkflowStepError`（`WorkflowInputError` 的子类），工作流记账后失败。
9. 工作流统一在一个步骤结束路径更新预算和累计用量，包含第一次无效结果、格式重试以及最终失败前的实际消费，不重复累计。
   `agents` 继续统计实际执行的逻辑步骤数，格式重试不另算一步；错误步骤记录本次消费，不写成功缓存。
   首次执行和格式重试均经过现有 semaphore；步骤开始及格式重试前检查剩余预算。预算检查仍不保证请求执行中绝不超额，不新增预算预留调度器。
10. journal 步骤键加入规范化的工具名单，排序去重；工作流 None 归一为五项基础工具，[] 保持为空；显式列出全部基础工具与默认配置得到相同工具键。
    恢复命中时不创建子 agent、不请求模型、不执行文件工具；工具权限不同的步骤不能命中同一个键。
    token 记录格式保持现有形式，不增加旧键兼容读取；此前未包含工具配置的旧步骤键不会命中新键。
    支持工具后的缓存仍是结果重放，不是文件系统恢复；用户需保留之前产生的文件，不能承诺重建已删除的副作用。

### 扩展验收矩阵

| 场景 | 断言 |
| --- | --- |
| 主模型和 workflow 执行 once | 经同一个公开创建入口、活跃登记、共享 session 和清理；结果由各自调用方处理。 |
| 工作流默认基础工具 | 省略工具参数时使用统一 once 的五项基础工具；不开放任务、通信、递归创建或 worktree 管理工具。 |
| 纯文本步骤显式 tools=[] | 模型请求不包含可调用工具；收到越权工具块不执行处理器、不产生文件副作用。 |
| 显式开放文件工具 | fake 模型实际调用处理器完成读写，经 Pre/Post hooks；拒绝时不执行。工具执行后还能再次请求模型得到最终步骤结果。 |
| 名称与白名单 | 并行同 label 不重名，中文 label 可展示；未知工具、非列表及模式不允许的工具均在副作用前失败。 |
| 客户端与输出上限 | workflow 使用注入的 fake/真实客户端及工作流上限，Lead 创建仍用默认上限；跨调用不改写全局 client/model/上限。 |
| 多回合和压缩用量 | 实际输入/输出 token 累计包括工具后的模型回合及摘要调用；本次实际请求数与 model_calls 一致。 |
| schema 第一次无效、第二次有效 | 两次均走统一入口及 semaphore；第二次收到上次结果和格式要求且无工具，先前文件操作只执行一次；一个逻辑步骤累计两次消费，缓存最终合格结果。 |
| schema 两次无效或执行失败 | 失败状态、失败前用量和错误原因保留；不写成功 journal，不遗留实例或分配；执行失败不另作格式重试。 |
| 历史归档与截断 | 仍保留当前委派；截断不执行任何工具，实际响应用量计入失败步骤。 |
| 并发与预算 | 多维度审查及格式重试均受并发上限约束；已无剩余额度时不发请求；超额结果按现有失败边界处理并保留实际消费。 |
| journal 恢复 | 同输入/schema/工具配置命中：新增 agents/tokens 均为零，不创建实例、不重跑文件工具；不同工具配置不误命中。 |
| 离线 demo/resume 与 host 接线 | CLI 和实际 Workflow 工具均通过统一入口；demo 不联网，resume 重放正确；host 不再绑定独立模型执行器。 |
