> 制定时间：2026-10-08

## 目标与范围

本轮处理四个新的深化机会，让规则集中在实际拥有行为的 module 内：

1. LLM adapter 保证交付的响应可消费，不把失败或截断参数转换成正常结果。
2. compaction 拥有历史压缩策略，host 只决定何时处理历史。
3. 后台结果领取同时完成全文保留与通知生成，不丢失输出尾部。
4. 在收益可证明时，将 Lead 的恢复状态与转换规则集中到 recovery。

本计划不替代[第一轮架构深化实施计划](2026-10-08-架构深化实施计划.md)。下列事项继续由原计划管理：memory 遗留 runtime、RuntimeContext、工具装配、TeammateSession、workflow / demo 拆分、host facade。

也不重做[10 月 6 日已完成的改造](2026-10-06-架构调整计划.md)：任务与 worktree 归属、core 会话状态、journal 用量、cron 持久交付和 flat 接线。

这里的历史压缩操作对象是 `messages`，不是 RuntimeContext 的运行时快照。后台结果指后台 bash 的输出，不是 cron 任务的持久投递。

## 约束

- 保留同步运行方式，以及 Lead、队友、subagent 的独立循环与工具权限。
- 沿用现有客户端 seam 和真实 / fake adapter，不新增通用 client 或依赖注入框架。
- 默认直接修改现有实现；不增加兼容层、第二套状态或通用存储抽象。
- 保留正常响应、工具名称、短输出通知、goal Stop、任务释放和 cron 确认语义。
- 本轮明确修正协议失败被当作正常响应、后台完整输出丢失、429 未打断连续 529 计数，以及压缩异常直接逃出循环的行为。
- 压缩失败本身不结束用户回合；不重复尝试同一次失败的自动或手动压缩。确实无法恢复的主模型错误仍结束本轮。
- 不新增第三方依赖。运行环境、编码、flat 生成和提交约定遵循 [AGENTS.md](../../AGENTS.md)。
- 每阶段独立提交。前一阶段未通过验收时，不在其失败状态上叠加下一阶段。

## 阶段 1：深化 LLM 响应有效性

### 目标文件

- 主要实现：[llm_client.py](../../src/agent_harness/llm_client.py)。
- 新增 `tests/test_llm_client.py`；按需要扩展现有 goal、workflow 和队友行为测试。
- host、subagent 和其他消费者只补必要的失败处理，不拆分循环或重做工具装配。

### 拟采用的 interface 与行为

继续使用 `client.messages.create(...)` seam。Responses adapter 在返回前验证自身协议结果；原生 Anthropic adapter 继续使用其现有返回对象，不增加统一转换层。

先检查顶层响应状态，再转换任何内容块，最后一次性交付 Message；任何工具块验证失败时，不返回批次中的其他工具。下表是项目拟采用的判定规则，不表示已经验证当前端点会返回所有输入。

| 输入情况 | 交付规则 |
| --- | --- |
| `completed`，包含完整文本或参数有效的工具调用 | 保留现有 Messages 形状、content 顺序与 usage |
| `completed`，无可见文本或工具 | 返回空 content / `end_turn`；合法空输出不等同于协议失败 |
| `incomplete`，原因是 `max_output_tokens`，无 function call | 返回文本 content / `max_tokens`，沿用 Lead 已有恢复 |
| `incomplete`，包含 function call | 抛协议异常；整批工具均不执行，不写入部分工具历史 |
| `incomplete`，其他原因或缺少原因 | 抛协议异常，保留原因；不当作可续写截断 |
| `failed`、`cancelled`、`queued`、`in_progress` | 抛协议异常；同步调用不交付这些状态的可执行结果 |
| status 缺失、为 null 或未知值；顶层不是 object | 抛协议异常，不猜测正常结束 |
| function arguments 为 JSON object 字符串，包括 `"{}"` | 解析后交付 dict；这包含合法的零参数调用 |
| function arguments 已为 dict | 保留当前直接接受 object 的实现行为 |
| arguments 缺失、null、空白字符串、非法 JSON、数组或标量 | 抛协议异常；不把这些情况当成合法零参数调用 |
| function call 缺少非空 name，或 call_id / id 都不可用 | 抛协议异常，避免不可分发或无法配对的工具块 |

新增 `llm_client.ProtocolResponseError`，继承 `Exception`，携带 `status`、`reason`、可选的 `tool_name` 和 `tool_call_id`，不继承 HTTP 错误类型。`recovery.with_retry` 的异常分支先按类型识别它并立即重新抛出，再运行现有 HTTP 错误判定；即使 reason 含 `429`、`529` 或 `overloaded` 也不能触发等待或切换模型。阶段 1 的目标文件因此包含 recovery。

本轮不新增截断工具的自动重放；阶段 4 同样沿用明确错误退出，避免引入另一项使用行为决策。

协议事实核对入口：[Responses 对象](https://platform.openai.com/docs/api-reference/responses/object)、[Function calling](https://developers.openai.com/api/docs/guides/function-calling)。本次补规格时，网页工具返回 503；直接访问及显式使用系统代理后的访问均返回 403，未取得正文。上述链接是核对入口，不作为已验证引用。实施者应记录核对结果；发现真实正常样本与表格冲突时，仅暂停受影响规则，报告具体差异，不静默增加缺省兼容分支。

### 迁移步骤与验收

1. 通过现有 `messages.create` interface 和 fake transport 复现两项已发现的问题。
2. 在 adapter 内调整状态判定顺序和参数解析，先验证正常文本、完整工具调用、零参数调用和 usage 不变。
3. 检查全部消费者：异常不能误触正常 Stop、handler 或 journal 成功记录；队友仍能报告错误并释放 assignment。
4. 验证截断文本仍能触发现有 Lead 恢复，截断工具不能留下孤立的 `tool_use` 历史。

消费者失败交付固定为：Lead 不触发正常 Stop、恢复未确认 cron；队友报告错误并走既有退出释放；subagent 通过其工具调用方交付错误；workflow runner 不写入成功 journal；goal 保持其 evaluator error 语义；memory 保持既有提取错误处理；压缩摘要进入阶段 2 的失败路径。若既有消费者已经满足规则，只补验证，不添加新处理层。

最少新增用例组：`completed_text_and_usage`、`zero_argument_tool`、`failed_response`、`incomplete_text`、`incomplete_tool_batch`、`invalid_arguments`、`missing_status_or_tool_identity`、`protocol_error_is_not_retried`。边界值用参数化覆盖。Lead 行为测试覆盖错误不执行 handler、不触发正常 Stop、cron 重入队。

不只测试私有 `_to_message` helper。核心证据必须经过调用方实际使用的客户端 interface，至少有一条 Lead 行为测试证明失败响应不会正常结束或执行工具。

**完成条件：** 调用方不需要读取 Responses 原始状态；有效响应不变，无效响应保留失败事实。depth 增加在已有 adapter 内，locality 集中在协议转换处，leverage 覆盖真实消费者。

## 阶段 2：集中历史压缩策略

### 目标文件

- [compaction.py](../../src/agent_harness/compaction.py)、[host.py](../../src/agent_harness/host.py)。
- `tests/test_compaction.py`；必要时扩展 scheduler 测试验证失败退出后的 cron 恢复。

### 拟采用的职责与行为

- 将 `host.prepare_context` 的完整策略移入 compaction，入口采用 `compaction.prepare_history(messages, active_request, *, enabled=True) -> CompactionResult`。所有压缩阈值与分层顺序由该 module 解释。
- 保留现有顺序：最新结果预算 → 数量裁剪 → 超触发线才缩减旧结果 → 仍超线才生成预览 → 最后摘要。
- 保留触发线与目标线的区别。低于触发线后不强求达到目标线，不改变工具配对和未读结果规则。
- host 仍负责自动、手动和被动压缩的触发时机；ManualCompaction 继续拥有手动请求状态。
- 摘要、输出保存或归档失败时，不提交任何半完成的历史替换。已经成功保存的原始输出和归档文件可以保留。
- 自动压缩失败后，本轮关闭后续自动压缩，使用原历史继续主模型调用。手动压缩失败后，将首次 compact 的工具结果改成错误说明，继续处理当前请求。
- 被动压缩摘要失败继续保留当前“归档加原始尾部”的行为；这项例外在 compaction 内管理，不扩散到 host。

### 历史提交与失败规则

`CompactionResult` 为只读数据对象，字段固定为 `applied: bool`、`reason: str | None`；reason 非空表示本次压缩失败。禁用自动压缩或无需修改时返回 `(False, None)`，不写盘、不调用摘要模型。

三种触发都在 `copy.deepcopy(messages)` 上执行完整历史变换；成功后用 `messages[:] = candidate` 提交。失败时丢弃 candidate，原历史及其嵌套块内容不变。必须保留外层列表身份；成功后的内容块不要求对象身份不变。`applied=True` 只表示实际历史修改已经提交。

摘要只接受非空、正常完成的文本。协议异常、额度截断、空摘要均视为摘要失败，不用占位摘要覆盖历史。

| 触发与失败 | host 后续行为 | 本轮再次尝试 |
| --- | --- | --- |
| 自动压缩：任一步失败 | 报告压缩失败，原历史继续进入主调用；不提前确认 cron | 自动压缩不再尝试；下一用户 / 后台回合重新启用 |
| 手动 compact：保存或摘要失败 | 保留已经执行的其他工具结果；向模型交付 compact 失败说明，继续循环 | compact 本轮不再提供，也不再执行；下一回合可重新请求 |
| 主调用确实超限：被动压缩摘要失败 | 若原始归档成功，沿用现有说明加原始尾部；提交后重试主调用 | 被动恢复最多一次 |
| 主调用确实超限：被动归档或历史提交前处理失败 | 原历史保持；恢复未确认 cron，交付明确错误并结束本轮 | 不用同样的超限历史重复主调用 |
| 被动恢复后主调用仍失败 | 使用现有主调用错误收尾 | 不再被动压缩 |

host 每次 `agent_loop` 创建局部 `automatic_compaction_enabled=True`，仅根据压缩结果关闭它；该值不跨回合共享，也不替代恢复状态。手动和被动触发不受这个值限制。

`ManualCompaction.completed` 改名为 `accepted`，表达本轮已接受过请求。首次调用返回现有请求说明，并在内部保留该 tool_result dict；重复请求只返回“本轮已请求”说明，不声称压缩成功。`apply_after_results(...) -> CompactionResult | None` 在完整结果已写回后执行事务；失败时直接更新保留的首次 tool_result 的 content，清除 pending，accepted 仍为 True。成功后历史已提交，不需要额外插入失败消息。

手动失败时对 compact 结果文本的更新，是事务回滚后的明确错误交付；其余消息和内容块仍保持原值。被动摘要失败但既有尾部方案成功提交时返回 `(True, None)`，摘要失败原因只报告到终端，不把已成功恢复误判为历史提交失败。

自动入口、手动入口和被动入口在 compaction 内捕获实际保存、归档和摘要异常，并返回失败结果；host 不靠包住整个工具循环来吞掉其他程序错误。主调用的错误收尾仍由 host 负责。手动摘要读取的是含完整结果的历史，失败后不得重跑已经执行过的工具。

为什么不直接结束：压缩是历史优化步骤，失败不证明主调用不可用。事务隔离解决半修改问题，本轮禁用再次尝试解决失败循环；真正的上下文超限由主调用与一次被动恢复判断。

### 迁移步骤与验收

1. 先补自动摘要、手动摘要和归档写入失败的行为证据，确认原始内容及待交付任务的状态。
2. 移动分层策略，迁移现有策略测试直接使用 compaction 的 interface，删除 host 中的重复编排。
3. 为三种入口接入深复制事务与 CompactionResult；被动入口采用 `reactive_compact(messages, active_request) -> CompactionResult`，同样由入口在成功后提交。
4. host 读取自动结果并关闭本轮自动尝试；读取被动结果决定重试或错误收尾。手动结果错误写回由 ManualCompaction 完成。
5. 更新重复 compact 的结果文本与测试，验证其他工具只执行一次、下一回合重新启用。

必须验证：`automatic_failure_then_main_success`、`automatic_failure_then_context_error`、`manual_failure_preserves_other_results`、`failed_candidate_preserves_nested_blocks`、`reactive_summary_failure_keeps_tail`、`reactive_archive_failure_ends_with_cron_restored`、`no_repeat_after_failure`。原有阈值、未读结果和配对测试继续保留。

**完成条件：** 改压缩顺序或阈值无需编辑 host；测试通过同一个 interface 验证完整策略。失败不会留下半替换历史，也不会遗失未确认 cron。

## 阶段 3：后台结果完整交付

### 目标文件

- [scheduler.py](../../src/agent_harness/scheduler.py)、[compaction.py](../../src/agent_harness/compaction.py)。
- `tests/test_scheduler.py`、`tests/test_compaction.py`。
- host 仅在通知注入确有需要时调整；不改变两种注入时机。

### 拟采用的 interface 与行为

- 保留 `collect_background_results() -> list[str]`，调用方仍领取 `task_notification` 文本。
- 输出不超过现有 200 字符摘要范围时，保持通知内容和一次领取行为。
- 超过摘要范围时，先保存完整结果，再生成包含摘要和全文路径的通知。落盘依据“是否将丢弃全文”，不能沿用较大的 `PERSIST_THRESHOLD` 而漏掉中等长度输出。
- 复用现有工具输出保存能力和 `core.tool_results_dir()`。启动后台任务时生成一次 `output_id = "background_" + uuid.uuid4().hex`，放在任务记录中；显示用 bg_id 不变。保存到 `background/<output_id>.txt`，与同步工具文件分目录，重启后 bg_id 重用不覆盖旧引用。
- 一次领取采用整批提交：先保存全部必要全文并构造全部通知，再移除该批内存记录。任何一项失败，整批不移除也不返回部分通知。
- 从选取 ready 到整批移除，全程持有 background_lock，包括本地写盘；不持有或申请任务锁，不执行 hooks 或模型调用。两个并发领取者因此不能领取同一结果；暂不引入领取中状态或另一把锁。

复用 `compaction.save_output`，增加仅供指定目录的 keyword 参数 `subdirectory: str | None = None`；同步调用默认路径与文件名不变。scheduler 调用时传 `subdirectory="background"`。当前导入方向允许这项复用，不为可能的未来变动提前拆新 module。

成功保存路径记到对应任务的 `saved_output_path`；这是已保存文件的事实，不是领取成功标记。整批失败后重试复用这些已存在文件，不重复生成新名字；文件已被删除时才重写。短输出不创建文件。通知仍保留原 200 字符 summary，长输出另加 `<full_output>` 路径。

领取失败时抛出 OSError，host 的两个通知注入入口捕获它并报告原因；`build_user_content` 返回已有同步工具结果，`inject_background_notifications` 不追加通知。不要因通知写盘错误跳过同步工具结果回填或重跑工具。下一次领取仍可重试完整批次。

只把实际文件 I/O 错误按 OSError 处理；其他程序异常保持整批记录并暴露错误，不改写成可重试的保存失败。

本阶段仍是进程内的一次领取，不新增跨进程队列、通知确认协议或重启后的任务恢复。
