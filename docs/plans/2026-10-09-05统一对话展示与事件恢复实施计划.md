# 统一对话展示与事件恢复实施计划

状态：步骤 1–6 已实施，离线验收通过。日期：2026-10-09。

## 目标与现状

用户在主对话区查看执行过程并处理审批，无需在消息、工具侧栏和审批弹窗之间寻找信息。
执行记录随会话保存，`/resume <id>` 后可以查看历史过程并继续交互。
实现统一展示和历史查看是本轮目的；核验与统计只展示已有或本轮实际采集的结果，不扩展为独立追踪系统。

实施基线为 `6117594`。当时已有事件通道、展示完成确认、审批交付和会话保存入口。
实施前 TUI 把工具与进度放在侧栏，审批使用弹窗；恢复主要依赖模型历史，不能还原完整过程。
现已由后端统一交付实时与历史展示记录；当前结构和实际验收见文末。

按职责调整目录已提交。下文沿用现有目录与模块；实施前重新核对工作区，不覆盖并行改动。
已有会话恢复规则见 [会话保存与恢复计划](2026-10-09-01交互会话保存与恢复计划.md)。
事件确认和审批等待规则见 [会话切换与审批交付深化计划](2026-10-09-04会话切换与审批交付深化计划.md)。

## 已确认的设计

- TUI 主对话区统一展示消息和用户关心的执行过程；工具详情和长输出可以展开。
- 审批改为对话内卡片，保留批准、拒绝、停止和关闭的后端规则。
- CLI 使用同一后端记录与顺序，以文本显示；无需复制 TUI 控件。
- 沿用 `~/.agent-harness/sessions/<id>.json`，在现有 `events` 中保存展示记录。
- `messages` 继续供模型调用和上下文压缩使用。展示记录用于还原界面，不整体加入模型输入。
- 前端只调用后端、展示记录并确认展示完成，不自行写会话文件或生成业务结果。
- 恢复历史不会重新执行工具、启动旧子 agent 或重新提交旧审批。
- 核验结果和统计必须来自真实执行记录，不照抄示例中尚不存在的能力。

不增加数据库、索引、独立事件文件、存储框架、新依赖或新的版本兼容分支。
不改变同步模型调用、后台生命周期、任务工作树规则、权限判定或 workflow 恢复机制。
不新增搜索、Notepad 等工具，也不为未发生的子 agent 内部步骤生成展示记录。

## 职责

在现有模块内完成，不新增记录管理器或保存线程。
文件分工的权威说明见 [runtime 说明](../../src/agent_harness/runtime/README.md)；下表只明确本轮新增职责。

| 现有位置 | 本轮职责 |
| --- | --- |
| `host.py`、执行工具的代码、`runtime/hooks.py` | 提供消息、工具请求与实际结果等事实；消息追加、事实发布和检查点顺序在这里接入；不直接生成 UI 控件或写文件 |
| `workspace/tasks.py`、`agents/subagent.py`、`runtime/scheduler.py` | 提供成功的 TODO 变化与已发布的执行状态；后台线程只发布事实，不修改 Lead 历史或会话文件 |
| `runtime/interactive_runtime.py` | 负责事实筛选、展示记录生成、会话归属、待保存记录消费、保存时机、恢复交付和真实回合统计；CLI/TUI 共用同一路径 |
| `runtime/session_store.py` 中的 `InteractiveSession` | 维护消息与展示记录，按 ID 追加一次，调用现有保存入口；保留写入失败后的 dirty 重试；不解析工具输出或决定审批 |
| 同文件中的 `SessionStore` | 校验会话字段，原子写入、读取、列出和删除文件；不处理事件交付或界面状态 |
| `runtime/interaction.py` | 保持事实交付的顺序、展示确认和审批等待规则；在审批创建与有效结束时提供事实，调用后端保存检查点；不解释业务结果或执行文件 I/O |
| `frontends/cli.py`、`frontends/tui/` | 渲染后端交付的记录，管理展开、历史加载和按钮状态；确认展示，提交输入与审批响应；不读写文件、补造历史或推断执行结果 |

执行代码提供事实，`InteractiveRuntime` 是事实转成展示记录的唯一负责人。
`InteractiveSession` 负责记录与上下文的维护和保存，`InteractionChannel` 负责交付；不在几个位置各自保存同一条事实。

## 展示范围

| 内容 | 显示与保存规则 |
| --- | --- |
| 用户输入、Lead 回复 | 保留正文和顺序；一次性子 agent 的已发布消息标明来源，不冒充 Lead 回复 |
| 工具调用 | 默认显示工具名、执行者和简短参数说明；参数全文可展开 |
| 工具结果 | 与调用 ID 对应；显示执行代码提供的状态，未知时显示“已返回结果”；摘要与全文可展开，仅缩短显示，不额外截断已有结果 |
| TODO | 成功更新后显示当时的列表和状态；没有标题时不编造 Plan 标题；恢复后保留各次更新，侧栏可保留最新状态 |
| 子 agent、后台任务进度 | 保存已发布的开始、状态变化、完成和失败；相同状态不重复刷屏 |
| 审批 | 卡片显示执行者、工具、参数与决定；等待决定时显示按钮，决定后显示结果并禁用按钮 |
| `/goal` 等命令结果 | 显示用户关心的结果；会话列表继续使用已有选择界面，不复制完整列表到对话 |
| 核验 | 只有工具或后端实际返回核验结果时才显示；工具成功不自动等于任务已通过验收 |
| 回合结束 | 显示真实结束状态、耗时、已记录工具调用次数、审批次数，以及已有 Lead 模型用量；未采集的统计不显示 |
| 保存 | 正常保存用状态提示，避免每次写文件插入一条消息；保存失败明确显示，保留现有重试规则 |
| 日志与内部通知 | 原始日志、状态快照、展示确认、保存成功通知和运行时服务日志不作为持久对话记录；原始日志保留在可选事件区 |

执行者由现有事件的 `source` 确定。工具调用与结果按调用 ID 配对，审批按请求 ID 配对。
配对同时限定会话、回合与执行者，不以工具名合并多次调用。
已知状态包括成功、失败、权限拒绝、停止前未执行和后台已启动；后台启动成功不代表后台任务完成。
状态只来自执行分支、明确异常或工具已有的结构化结果。现有字符串工具结果不能靠匹配 `Error` 等词判断状态；没有可靠依据时保留原结果并显示“已返回结果”。
状态保存在展示记录中，不为显示状态改变模型协议或重写所有工具的返回格式。
工具调用次数只统计实际发布的调用，审批次数只统计实际请求；不把重复渲染和恢复计入统计。
第一版不新增完整调用链追踪和交接统计；用量标明 Lead 范围，不把它说成全部子 agent 的总用量。
回合结束摘要保存后在恢复时原样展示，不用恢复后重置的用量重新计算。

## 保存与恢复

### 记录形态与唯一入口

扩展现有 `events`，保留交互、命令等已有记录用途。
新增展示记录包含稳定 ID、时间、类型、来源、回合 ID 和 JSON 内容；工具或审批记录保留对应调用或请求 ID。
列表顺序是该会话的显示顺序；通道的进程内序号和代次用于交付，不能当作跨进程记录 ID。
展示记录与原有交互记录明确区分，避免同一次输入同时渲染 `user_input` 和 `user_message`。
命令、模型消息、工具和进度从各自的事实生成记录，不把格式化后的屏幕文本作为权威数据。
后端使用明确的记录类型列表，不按“能显示”就保存所有通道通知。

通道接受事实时，在同一顺序下生成一次稳定记录 ID，并向后端内存队列提交副本；实时通知和保存记录使用同一个 ID。
这一步只入队，不写文件，也不等待业务锁或前端展示。保存队列与前端的 `next_event()` 分开，不能竞争取走同一通知。
`InteractiveRuntime` 消费队列，筛选记录类型与会话 ID、代次，生成展示记录并交给 `InteractiveSession` 追加。
原有交互摘要继续用于会话列表，标明为摘要；前端只渲染展示记录，不再次渲染摘要。

### 保存时机与边界

- Lead 消息采用“追加消息历史 → 发布对应事实 → 消费待保存记录 → 保存上下文”的顺序。调整当前 `host.agent_loop` 先保存再发布的顺序，让消息与对应展示记录写入同一次文件保存。
- 用户输入、命令结果、TODO 成功更新和回合结束采用相同检查点；第一条交互先取得会话 ID，再发布事实。原有摘要的追加不再抢先单独保存。
- 工具请求在权限检查和执行前经过检查点；一次模型响应中的消息和工具请求可以合并保存，但不等整轮工具执行结束。
- 后台状态只归属已有会话；没有用户交互时不因此创建会话。Lead 在消息与工具检查点、空闲轮询和审批等待轮询中消费并保存队列；这些工作不会额外发起模型调用。
- 正常切换前消费旧会话的待保存记录并保存，失败时沿用既有规则拒绝切换。退出先让所属后台结束，再消费最后状态并完成最终保存；切换后旧代次的迟到事实丢弃，不能进入新会话。
- 保存失败保留内存记录并标记待保存，下一次保存重试；不能因重试重复追加。
- 保存成功或失败通知不反过来触发自身保存，避免递归与重复提示。

审批记录与保存必须由审批执行路径触发：

1. 通道生成请求 ID 和请求事实，离开通道锁，调用当前执行上下文中的后端检查点，完成保存尝试后再允许前端取得该请求。
2. 阻塞等待期间，现有审批等待循环定期离开通道锁调用同一检查点，保存新到的后台记录。不能只依赖 `InteractiveRuntime._run()`，因为此时 Lead 线程就在等待审批。
3. 批准、拒绝、停止或关闭实际结束请求时，生成一次结束事实并在返回工具执行路径前经过检查点。无效或重复响应不生成新决定记录。

检查点由 `InteractiveRuntime` 随执行上下文提供，同步 once 子 agent 继承；独立后台只入队，不获取 Lead 锁或调用保存。
检查点为空队列且上下文未变化时不重复写文件。审批轮询不因 dirty 状态每次重试并刷错误；失败后在新的记录或其他既有保存时机重试，不把写入失败当作用户拒绝。
前端看到等待卡片不等于获得审批权，按钮仍以 `next_approval()` 的有效请求为准。

保存只由 Lead 执行线程执行，不在通道锁中写文件或获取 Lead 执行锁，不等待前端展示完成。
后台发布不等待文件写入。长时间同步模型调用或工具执行中，后台事实先留在队列，直到下一检查点才落盘；这段时间异常退出可能丢失尚未保存的记录。
模型或工具中尚未形成完整记录的局部输出仍不保证保存。
本轮不承诺磁盘写入失败时能恢复尚未落盘的内容，也不增加文件系统事务。

### `/resume` 的显示恢复

后端恢复上下文时，向前端交付已保存的展示记录。
前端清理旧对话，按保存顺序重建新对话，再接收新的实时记录。
以展示记录为显示来源，避免再遍历 `messages` 重复显示同一消息和工具。
模型历史压缩不删除已保存的展示记录，两者按各自用途维护。

会话结构遵循 [项目规范：正向开发](../../AGENTS.md#正向开发)。
本轮直接更新会话读写与字段校验，使消息历史和展示记录满足同一当前结构。
读取文件时只按当前结构校验，不按创建日期区分新旧；符合要求就恢复，不符合就明确报告缺失或非法字段，保留文件和当前会话。
空会话允许空展示记录；已有用户或模型消息却缺少对应展示记录的文件不能当作完整历史静默恢复。

历史审批只读显示已记录的决定。
保存时仍在等待的审批显示为“上次中断，未继续执行”，不恢复按钮或自动批准。
尚无结果的工具显示为“结果未记录，请核对当前状态”，不能断言它没有产生文件或其他效果。
后台状态标明是历史记录；不会因为历史显示“运行中”就恢复线程。
恢复过程中新增的中断说明不得在重复 `/resume` 时不断追加同样的消息。

## 前端交互

TUI 复用现有 Textual 控件，在主对话区增加工具、TODO、进度、审批和结束摘要的展示。
详细参数和长输出默认收起，正文保持 Markdown；窄终端下也能看到进度和审批。
保留输入框、命令补全、会话选择、停止和关闭操作。
侧栏只保留当前状态与可选原始事件，不再是执行过程唯一可见的位置。

审批卡片只有收到 `next_approval()` 返回的有效请求后才启用按钮。
历史记录或普通事件不能创建可执行审批。
响应仍调用后端 `respond(request_id, generation, decision)`；后端处理过期、重复响应和取消。
停止、关闭、切换或决定后移除可操作状态，迟到点击不能执行工具。
沿用先展示前置事件、再确认、再开放审批的顺序，保留有限批次消费，持续日志不能阻挡审批。

CLI 保留唯一 stdin 读取者和既有线程安排，提供相同信息的文本形式。
恢复时能查看保存的对话记录和执行摘要，历史审批只打印结果，不询问是否批准。
展示采用同一记录 ID 去重，实时展示、恢复展示和后端保存重试均不产生重复条目。
界面可以只挂载最近一段记录，但保存不因界面上限被删减；TUI 提供查看更早记录的入口。

## 实施顺序与验收

| 顺序 | 工作 | 完成条件 |
| --- | --- | --- |
| 1 | 核对 Git 基线、既有事件和保存入口 | 明确改动文件与职责；保留所有无关改动；不引入旧格式兼容分支 |
| 2 | 接入内存队列、唯一记录生成路径、消息与工具检查点 | 消息与展示记录同次保存；执行前保存工具请求；实时与保存顺序、ID 一致；工具状态有实际依据 |
| 3 | 接入后台安全点、TODO、审批请求与决定、真实回合摘要 | 等待审批期间能读取已保存请求和新后台状态；没有死锁、递归保存或重复追加；统计来源可验证 |
| 4 | 扩展当前结构校验、恢复交付与中断显示 | 不符合当前结构的文件报错并保留当前会话；恢复、续聊、再次恢复和压缩后历史不遗漏；跨目录顺序、来源、工具配对和审批结果正确；不调用模型或重执行工具 |
| 5 | TUI 统一对话与内联审批，CLI 接入同一记录 | 运行过程在主对话可见，详情可展开；历史与实时不重复；窄屏和大量事件下仍可操作 |
| 6 | 回归、使用验证、文档更新与提交 | 下列验收通过；计划记录实际结果；README、开发笔记只记录最终行为 |

关键验收覆盖：

- 真实临时会话文件保存与恢复多轮消息、交错工具、TODO、子 agent 状态，确认显示顺序和来源。
- 消息检查点写入同一份消息与展示记录；在工具执行前读文件，能找到对应请求，保存重试沿用同一记录 ID。
- 完整模型历史仍按原协议发送；展示记录不进入请求，不破坏压缩、goal、任务、工作树与 TODO 恢复。
- 当前结构的会话恢复、继续一轮、再次恢复和压缩后恢复，验证展示记录完整保留，不能只覆盖进程内显示。
- 不符合当前结构的会话文件明确报错，原文件、当前上下文和目录均保留；不调用回填、迁移或旧结构读取逻辑。
- 等待审批时退出或中断，恢复后只有历史卡片，无批准按钮，也不会执行工具。
- Lead 与同步 once 等待审批时，另一个线程发布后台状态；无需用户作出决定就能从文件读到该状态。长模型或工具期间排队的状态在下一检查点保存。
- 审批通过、拒绝、停止、关闭、重复点击和旧代次响应均符合现有后端规则。
- 后台并发发布、空闲保存、跨目录切换和迟到事件不串会话；保存失败后重试不丢记录、不重复。
- 退出等待后台结束后仍保存最后状态；通道锁中不执行文件写入，保存不等待前端确认。
- 权限拒绝、执行异常、停止前未执行、后台启动与完成、普通字符串结果分别显示可信状态；含 `Error` 的正常结果不被前端猜成失败。
- 保存通知不会循环保存；原始日志不让会话文件无意义增长。
- TUI 使用现有无头测试验证卡片顺序、展开、加载更早记录、窄屏及大量事件下的审批和输入。
- CLI 验证相同记录顺序、恢复历史不询问审批、唯一 stdin 读取规则和输出异常后的关闭。
- 回合统计与实际调用数对应；恢复不改变既有摘要，未知核验与用量不生成虚假结论。
