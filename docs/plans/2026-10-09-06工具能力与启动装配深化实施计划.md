## 1. 问题与目标

### C1：共用工具定义与执行者绑定

[registrations.py](../../src/agent_harness/registrations.py) 与 [subagent_session.py](../../src/agent_harness/agents/subagent_session.py) 各自维护八项相同能力：`bash`、`read_file`、`write_file`、`edit_file`、`glob`、`list_tasks`、`claim_task`、`complete_task`。
二者还分别处理执行者工作目录、任务归属和任务板文本。基础文件操作已经共用；重复发生在工具定义和身份绑定层。

目标：共用 schema、handler 绑定和任务工具文本由一个工具模块维护。Lead 与子 agent 只负责选择各自开放的能力。保留双方已有差异，不把子 agent 权限扩大到 Lead 的范围。

### C2：显式启动装配与 runner 选择

[host.py](../../src/agent_harness/host.py) 在导入时登记示例 workflow、覆盖 `RUNNER_FACTORY`、配置工具注册器并创建 `GOAL`。
测试和离线入口先注入 runner 后，后续导入或重新加载 host 会改变已经选好的实现。入口与测试依赖隐含导入顺序。

目标：上述应用装配通过明确的初始化入口完成。导入 host 不再覆盖 runner 或创建目标控制器。生产、离线 demo 与测试各自明确选择执行配置。

收益门：C1 必须减少共用能力的维护位置；C2 必须消除 runner 被导入覆盖的行为。仅移动文件或把赋值包进函数，不算完成。

最高有效测试边界：工具定义与 handler 一起交付给真实调用方的入口，以及“选择 runner → 导入 host → 显式初始化 → 启动”的顺序。内部辅助函数名称不是验收对象。

## 4. C1 设计契约

### 4.1 共用定义与绑定

建议接口为 `shared_tool_definitions(owner, *, profile)`，返回按名称索引的 `ToolDefinition`。`profile` 仅支持当前实际存在的 Lead 与 child 两种表面差异，不扩展成通用角色系统。

共用属性 schema 只定义一次。描述差异、Lead bash 的 `run_in_background` 参数及现有任务缺失错误的大小写差异，在这个模块集中表达。每次构造获得独立的嵌套 schema，修改一个会话的定义不能污染其他会话。

`file_tools` 提供按 owner 绑定五项工具的唯一实现。绑定的是身份，每次执行才读取 `tasks.assignment_cwd(owner)`。会话创建后的任务认领、完成、切换或无效分配，都使用调用当时的状态。
Lead 现有 `run_agent_*` 接口直接使用这套绑定逻辑。不得让它们与 child 保留两套目录解析规则。

任务工具统一委托 `tasks.list_tasks/claim_task/complete_task`。底层任务校验和存储仍由 tasks 负责。Lead 的 owner 为 `agent`，child 的 owner 为子 agent 名称；通信中使用的 `lead` 不替代任务 owner。

八项定义都同时携带 schema 和 handler。调用方可从同一批定义生成模型工具与处理器映射，不再独立列两张共用能力表。Lead 原有工具顺序，包括共用项之间的专有工具，必须保留。

### 4.2 能力选择与权限

| 调用者 | 默认基础能力 | 条件能力 | 仍由谁决定 |
| --- | --- | --- | --- |
| Lead | 五项文件/bash 工具 | 三项任务工具及原有 Lead 专有工具；bash 可后台执行 | registrations 与现有 host 执行路径 |
| once child，无任务 | 五项文件/bash 工具 | 无任务工具、无持久通信工具 | subagent 模式选择与白名单 |
| once child，绑定任务 | 五项文件/bash 工具 | 三项任务工具 | subagent 创建条件与白名单 |
| persistent child | 五项文件/bash 工具 | 三项任务工具、`send_message`、`submit_plan` | subagent 生命周期与白名单 |
| workflow step | 当前 once child 能力 | 以实际传入的 `tools` 白名单进一步限制 | workflow 经已有子 agent 创建接口委派 |

`tools=None` 保留当前默认集合，`tools=[]` 不开放工具，非法名称继续在创建前拒绝。child bash 的 schema 和实际 handler 都不接收后台执行参数。

共用模块不判断资格，也不执行授权。child 路径仍依次执行：工具可用性检查 → 计划门禁 → `PreToolUse` → handler → `PostToolUse`。前三步拒绝时不产生工具副作用，也不触发后置 hook。

保留 05 的 `call_tool_handler(..., on_status=...)`、TODO 事实发布和保存检查点，以及 host 消息/工具事实与检查点的顺序。共用模块只提供定义与绑定；执行路径提供事实；InteractiveRuntime 仍是展示记录生成与保存的负责人。抽取后验收“工具执行 → 状态记录 → 保存 → 恢复”，不将这部分职责转入 shared_tools。

## 5. C2 设计契约

建议在现有 host 内新增 `initialize_runtime()`，不另建 bootstrap 框架。它只负责示例 workflow 登记、注册器来源配置和目标控制器的初次配置。

1. 导入 host 不执行上述三项装配，也不设置 `workflow_runtime.RUNNER_FACTORY`。
2. 保留 workflow runtime 现有默认 `RUNNER_FACTORY = SubagentRunner`。它构造时读取当前 `core.client/MODEL`，无需 host 重复赋值。
3. 首次初始化配置应用。成功后标记已初始化；重复调用保留同一 GOAL 和已选 runner，不重新配置注册器或覆盖 workflow。初始化失败时不标记完成，可明确重试。
4. 如果调用方已显式 `configure_goal()`，初始化保留该控制器。需要主动替换时继续使用现有 `configure_goal()`，不靠重新导入实现。
5. `InteractiveRuntime.start()` 在已有生命周期锁内、设置 `_started` 和启动线程前初始化。CLI/TUI 默认路径都经过这个入口；直接导入和构造对象不启动后台服务。
6. workflow demo CLI 分支显式调用 `register_workflows()` 并设置离线 runner，再运行 demo。它不依赖交互运行时启动。
7. 直接使用 host API 的脚本或测试显式初始化。测试是否要生产 runner、离线 runner 或自定义 GOAL，由 fixture/用例明确设置，不让 host 的导入替它做选择。

配置入口不请求模型、不启动线程或 cron、不写运行时文件、不改变工作目录。现有服务启动仍属于交互运行时的执行阶段。
首次装配先完成可能失败的目标配置与校验，再发布 workflow 和注册器配置。失败后不得标记已初始化；start 保持 `_started=False` 且未创建执行线程。修正配置后可重试，已有 GOAL 与 runner 不被失败或重试覆盖；不增加事务框架。
这里的幂等范围是当前 host 模块实例。重新加载 host 用于测试，不承诺重载后保留全部会话状态；必须保留外部 workflow 模块中已注入的 runner。
本次只消除列出的应用装配副作用，不承诺 core 等所有依赖导入完全无副作用。
