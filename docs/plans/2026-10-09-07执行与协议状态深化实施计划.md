## 1. 问题、目标与证据

### C1：工作流并行执行的结算与收尾（Strong，优先）

[workflow_runtime.py](../../src/agent_harness/workflows/workflow_runtime.py) 的 `ExecutionState.parallel/pipeline` 使用默认 `asyncio.gather`。
一个分支失败后，异常到达 `WorkflowTool._call_locked`，后者关闭 journal、保存快照并返回。
其他分支可能仍在 `asyncio.to_thread` 中运行，随后才记账与写入成功结果。

审查通过真实 `WorkflowTool.call` 和离线 runner 复现：失败分支消耗 3 tokens，迟到分支已开始运行。
运行返回 failed 时，快照为 agents=1 / tokens=3；迟到分支完成后，内存为 agents=2 / tokens=8，写 journal 抛出 `ValueError: I/O operation on closed file.`。
因此最终快照遗漏实际用量，迟到成功结果也无法缓存。

同一区域另有已复现的预算分叉：预算为 1，首步消耗 5，脚本捕获超额异常后，第二步仍可消耗 1，最终返回 completed / tokens=6。
原因是 task 已记实际消费，但 `Budget.add` 超额时保留原 spent，后续剩余额度判断没有依据实际消费。
用户已确认将这一根因一并纳入结算职责，实际消费先记账，超额后禁止新调用。

目标：运行结束晚于已启动步骤结算；实际用量有唯一计数来源；失败、缓存与预算判断都依据同一运行事实。

### C2：统一普通工具执行的共同规则（Strong）

[host.py](../../src/agent_harness/host.py) 和 [subagent_session.py](../../src/agent_harness/agents/subagent_session.py) 分别维护 `PreToolUse → handler → PostToolUse`。
Lead 用 `if blocked` 判断拒绝，child 用 `blocked is not None`；[hooks.py](../../src/agent_harness/runtime/hooks.py) 的既有契约是返回第一个非 None 结果。

实际入口复现：hook 返回空字符串时，Lead handler 与 PostToolUse 各执行一次，child handler 执行零次。
目标：共同拒绝契约和同步执行顺序只有一份实现，Lead 与 child 保留各自循环和能力差异。

### C3：集中子 agent 计划协议的状态转换（Worth exploring）

[subagent.py](../../src/agent_harness/agents/subagent.py) 的 `plan_gates`、`plan_request_ids`、`plan_gate_versions`、`pending_requests` 共同表达计划状态。
创建、授权、提交、审核、收信、持久工作收尾和退出分别读写这些记录，并读取 tasks 的任务与分配版本。
测试需要手工构造多张字典，修改一种转换时难以只检查一个位置。

`pending_requests` 同时记录计划与关闭请求，请求 ID 和退出清理也是共享逻辑。
目标：协议 module 拥有唯一状态及转换规则；subagent 保留通信与生命周期，tasks 保留任务分配事实。
本候选尚未发现新的确定行为错误，收益门是减少状态维护位置，不以拆文件本身作为完成依据。

## 4. C1 推荐设计与行为契约

### 4.1 并行等待和运行收尾

推荐保留当前“不主动取消其他分支”的语义，但必须等待同组全部分支结束后再传播失败。
`parallel` 和 `pipeline` 共用一个内部等待实现；成功结果继续按输入顺序返回。
失败时保留首先观察到的业务异常，不让迟到的成功或另一个失败把本组变成成功。
`parallel` 的成员工厂 `thunk()` 同步抛错时，已接收成员按普通失败策略完成并结算，尚未接收成员不启动；构造异常纳入本组首次失败，不遗留未等待协程。
pipeline 每项内部仍按阶段顺序执行；某项失败后不进入该项后续阶段，其他项继续其已有流程。

运行入口负责最后一次结算屏障，登记对象是完整步骤，不能仅登记已经进入线程的 runner。
有效步骤进入 `agent()` 后，在等待语义键锁或并发槽之前登记；登记持续到缓存回放或执行、校验、记账、结果提交全部完成，并在每条退出路径解除。
`parallel/pipeline` 进入时也登记本组编排，持续到组内成员全部结束。普通收尾期间，已登记组的后续成员或 pipeline 阶段属于原有工作，可以继续；不能因其尚未进入 `agent()` 而漏掉整组或提前关闭 journal。
父子 `ExecutionState` 共用同一个运行级登记与收尾状态，优先深化已有 `ExecutionLimits`，不建立第二套通用调度器。

脚本返回、异常或取消后进入收尾，拒绝未属于已登记工作的独立新步骤或新编排组，拒绝时不调用模型、不写 journal。
普通返回或业务异常时，已经登记的工作继续原有流程并全部结算，包括尚在等待锁或并发槽的步骤，以及已登记组内的后续合法调用。
取消或预算超额时，按第 4.3、4.4 节阻止尚未启动的调用；已经开始的线程仍须等待并结算。
只有登记为空、没有未结算 runner 或结果提交时，才允许关闭 journal、保存最终结果并释放运行锁。
即使脚本在编排原语之外抛出异常，也必须执行这一屏障，避免 resume 与迟到执行同时写入。

不支持任意用户脚本绕过运行时追踪，直接创建线程并写 journal。
运行时不新增超时结束策略；一个已有 runner 不返回时，本次收尾会等待它，由现有工具或模型调用超时处理。

| 收尾原因 | 已登记但尚未启动的调用 | 已启动的调用 | 调用方得到的终态 |
| --- | --- | --- | --- |
| 普通返回 | 继续已有工作 | 等待并结算 | 已有工作结算后完成；结算中出现失败则 failed |
| 业务异常 | 继续已有工作 | 等待并结算 | failed，保留首先观察到的失败 |
| 预算超额 | 禁止新执行和格式修复 | 等待并按实际消费结算 | failed，即使脚本捕获超额异常 |
| 外层取消 | 退出等待，不启动调用 | 等待并按实际消费结算 | 保存 failed，释放运行锁后重抛取消 |

普通失败继续其他已登记工作，意味着这些工作仍可能产生模型调用和文件副作用；用户已确认这一策略。

### 4.2 结果、失败与恢复

- 成功且 schema 有效、步骤提交时累计消费未超额的结果才写成功缓存；失败或取消步骤保持无新的成功缓存。预算恰好用满时允许当前有效结果提交。
- 并行另一分支失败时，已有效完成的步骤仍可保存成功结果；恢复时可重放这些结果。
- 执行、格式修复和失败调用的已知实际用量各记录一次；缓存重放不增加消费。
- 关闭 journal、保存输出/最终快照、发布最终通知和返回或重新抛出取消，均晚于全部已登记工作退出与实际调用结算。
- 最终快照的本次/累计消费与 task 内存一致；返回后不存在该运行继续更新用量或写 journal 的任务。
- 保留原有运行名称/参数校验、语义缓存键、同键去重、并发上限、agent cap、嵌套限制和跨进程运行锁。
- 不改变已经发生的文件或模型副作用，不把“运行 failed”解释为所有并行步骤都没有执行。

### 4.3 实际预算

推荐让预算始终记录实际消费，超额时先更新消费，再报告超额；禁止 task 和 Budget 各自拥有不一致的累计 token 事实。
以现有 `Budget` 的累计 token 为权威事实；task 的 cumulativeUsage 从它更新，本次 usage 由累计值减去恢复起点得出，不保持两套独立 token 加法。
执行请求和格式修复返回或抛出带已知消费的 `WorkflowStepError` 后，各自立即结算一次，再决定是否允许后续请求，避免只在完整步骤最后检查预算。
保留现有 agents 计数口径：一个真正开始 runner 的 agent 步骤计一次，同步骤格式修复不另加 agents；缓存、等候中取消和启动前拒绝不计执行消费。agent cap 仍是原有调用限制，与实际执行用量分开。

预算达到上限后，禁止新执行及格式修复，但有效缓存仍可回放。
预算超额是本次运行不可恢复的预算失败：即使脚本捕获异常，后续不发起新模型调用，本次运行也不能最终标为 completed。
已经开始的并行调用继续按实际消费结算，最终消费可以超过配置预算；不承诺从事后检查改成调用前的硬上限。
恢复继续读取历史累计消费，不清零预算。未超额但恰好用完预算的纯缓存恢复仍可完成；已超额运行不因捕获异常或恢复而变成预算内成功。
超额前已提交的成功缓存保留；超额后结算的迟到步骤只记录实际消费，不新增成功缓存。既有 journal 的累计消费字段继续写实际值，文件结构不变。

**错误优先级：**结算必须先记录真实消费和超额事实，再决定传播哪个异常，不能让记账时抛出的预算异常覆盖正在处理的业务错误。
同一步先发生 runner/校验业务错误、结算又超额时，向外保留原始业务错误，预算仍记录超额并禁止后续调用。
没有业务错误但发生超额时，按原有错误文本报告预算失败。
并行组保留首先观察到的步骤失败；迟到分支的业务或预算错误不得覆盖它。运行级超额状态独立保留，即使脚本捕获步骤失败，最终仍不能标为 completed。
不新增持久化错误字段：最终 `result.error` 使用上述优先级，实际消费写入已有 usage/cumulativeUsage 字段，预算事实可由配置上限与累计消费判断。

### 4.4 取消终态与异常传播

显式处理 `asyncio.CancelledError`；它继承 BaseException，不能只依赖当前的 `except Exception`。
取消进入运行级收尾后，不再启动新 runner、等待队列中的模型调用或新的格式修复；已在执行的格式修复按已启动调用结算。
被取消步骤不写新的成功缓存，取消前已完整提交的缓存保留；实际已知消费仍记录一次。
尚未进入线程的已登记步骤退出等待并解除登记，不凭空增加 agent/token 消费。

取消路径的顺序是：标记取消并关闭新调用入口 → 等待并结算已启动线程、清理登记 → 关闭 journal → 保存 failed 输出和最终快照 → 发布最终通知 → 释放运行锁 → 重新抛出原 CancelledError。
沿用现有 failed 状态，不新增 cancelled 持久化状态；最终 `result.error` 使用明确的取消说明，例如 `Workflow cancelled`。
不能吞掉取消并返回普通成功/失败结果，也不能把普通业务异常转成取消；取消期间的业务/预算失败不能替换对调用方传播的取消异常，但仍记录实际消费。
收尾等待需要避免再次取消打断结算；同一运行重复收到取消时，不提前释放锁、不重复计费、不重复关闭或保存终态。
以上最终保存以文件写入成功为前提；文件 I/O 失败沿用现有异常处理约束，不把未成功保存描述为已保存。

## 5. C2 推荐设计与行为契约

共同执行提供“检查”和“同步执行”两个内部动作，而不是让每个调用方重写钩子顺序。
拆成两步是因为 Lead 在检查通过后可能分派后台任务；不得为了单个入口改变后台行为。
检查结果须明确区分放行、拒绝、停止，输出拒绝文本；不能用文本真假值决定是否执行。

调用方保留原有执行前停止检查；共同检查中的顺序是：child 能力检查 → child 计划授权（如有）→ PreToolUse → 调用方停止检查（如有）→ 处理前置拒绝或放行 → 同步执行或 Lead 后台分派。
计划授权和 PreToolUse 都只有 None 表示放行。空字符串、False、0 都是拒绝结果，保持现有 `str(...)` 文本转换。
child 不可用工具保持当前错误文本和先拒绝顺序，不运行计划授权或 PreToolUse；Lead 的未知工具路径保持当前处理顺序与结果。
对使用停止检查的调用方，PreToolUse 返回拒绝结果后仍须检查停止，不能先因拒绝直接返回。
停止和 hook 拒绝同时生效时，结果为 stopped，保留 Lead 的 `Interrupted before execution`、is_error 和状态事实，不生成 denied 结果。
计划授权或工具资格已经拒绝而未进入 PreToolUse 时，保留 child 的既有先拒绝顺序；不为 child 增加原本不存在的停止协议。

同步执行复用现有 `call_tool_handler` 的错误转换和 `on_status`，随后调用 PostToolUse。
拒绝、停止不运行 handler 或 PostToolUse；已经调用 handler 后，保持原有后置 hook 语义，不根据结果文本猜测成功或失败。
hook 自身异常继续按既有调用链传播，不在本阶段设计新的容错协议。
共同检查结果只承载放行、拒绝或停止及必要文本；同步执行保留 `call_tool_handler` 状态回调。不新增第二份工具结果状态存储，也不从空文本或 `Error:` 前缀推断是否执行成功。

Lead 的 compact 继续绕过普通执行路径。后台任务只做一次 PreToolUse，PostToolUse 仍由 scheduler 在实际完成后执行一次。
共同检查结束后、后台启动前再次核对停止状态，保留停止审批后不启动命令的既有保证。
工具事实与保存检查点仍由原执行路径负责；共同执行只提供明确状态，不直接生成对话展示记录或写会话文件。
保留 TODO 提醒计数、通知回填、工具调用 ID 配对及完整响应才执行工具的规则。

## 6. C3 推荐设计与行为契约

### 6.1 状态所有权与依赖

在协议 module 内用按子 agent 存放的计划记录集中门禁、当前请求 ID 与任务版本关联，取代三张公开 `plan_*` 字典。
保留一份按 request_id 索引的协议请求存储，计划与 shutdown 共用；索引表达定位关系，不能再由多个模块独立写入。
门禁和请求审核状态不是同一阶段：Lead 批准请求后，child 尚未接收有效回复时，门禁仍为 pending。
不得为了“只有一个 status”而提前放行工具。

subagent 通过动作与只读查询调用协议 module；直接修改字典的 host 重导出、fixture 和测试一并删除或替换。
保留正在使用的模型工具处理函数作为编排入口，不保留旧内部状态字典的兼容视图或双写。
现有 request ID 格式、消息 metadata、普通反馈文本和关闭协议保持不变。

tasks 增加或复用一个一致查询当前分配版本/任务 ID 的入口，替代协议路径直接读取内部字典。
固定锁顺序为任务锁 → 子 agent/协议锁；协议与活跃登记需要同步时使用同一已存在的子 agent RLock，不引入反向锁依赖。
该 RLock 仍由 subagent 的进程运行时拥有，并显式传给协议 module；协议 module 不反向导入 subagent 取得锁，也不另建一把协议锁。
协议 module 不持锁调用 MessageBus、模型、前端或任务变更；subagent 取得转换结果后完成投递和必要生命周期状态更新。

### 6.2 转换与验收

| 动作 | 必须保持的行为 |
| --- | --- |
| 创建 | 按 require_plan 登记 required/not_required，关联当前任务版本；创建失败和线程启动失败无残留 |
| Lead 要求计划 | 设置 required，使旧当前请求失效，发送既有 plan_request；未提交前不生成审批请求 ID |
| child 提交 | 记录当前任务 ID/版本，设 pending；同一当前计划重复提交被拒绝；发送请求后进入等待 |
| Lead 审核 | 类型、身份、任务 ID、版本、当前请求和 pending 状态匹配才接受；只更新请求决定并投递回复 |
| child 应用回复 | 重新校验发件人、收件人、request_id、任务/版本及决定一致性；有效接收后才更新门禁 |
| 拒绝后重交 | 接收拒绝后保持工具受限，重新提交获得新 ID；旧回复不能改变新计划 |
| 任务/委派变化 | 旧版本请求不能放行当前工作；保留当前 required/not_required 重置语义 |
| 持久工作收尾 | 仅在最终回答后按现有条件释放完成分配与重置协议；未完成任务继续占有，不自动认领或结束实例 |
| shutdown 与退出 | 保留类型/身份匹配；清理该实例相关计划与关闭请求；已发送给 Lead 的确认消息仍可被消费 |

生命周期 `record.status` 仍归 subagent，不并入协议持久化，也不由协议 module 操作线程。
subagent 在协议动作的既有锁范围内同步 waiting_approval/working，避免状态转换中间被其他线程观察为可执行。
工具白名单、任务目录、工具授权、持久历史与通信仍使用统一子 agent 执行入口。
计划审批不和面向用户的权限审批合并，不新增一个通用状态机框架。
