# 工具调用协议与 Todo 职责边界实施计划

状态：草案，待审核后执行。

## 目标与范围

模型负责选择工具、给出参数内容，以及通过 `todo_write` 提出和更新计划。Provider 负责工具调用协议转换；执行层负责工具分发；Todo 工具负责最小参数检查、保存和事件发布；前端负责展示。

本次以现有工具调用链为基础，删除 Todo 隐式提醒并收窄接口边界。模型使用 API 的工具调用接口，普通文本中的 JSON 不作为工具调用执行。

实际交付为：删除 Todo 提醒、移除 Todo 字符串二次解析、补齐最小参数检查，并返回清单状态统计。协议链主要核对和复用，不将减少 JSON 格式错误或降低 token 消耗列为本次完成指标。

## 职责约定

### 模型

决定是否调用工具、参数内容、Todo 拆分和各项状态，也决定一次提交哪些调用、何时依据结果生成后续调用。运行时不猜测某项是否完成，不根据工具结果自动修改 Todo。

### Provider

将 API 已标识的工具调用转换为统一的 `Block(type="tool_use", id=..., name=..., input=dict)`，负责参数解析和协议错误。同步和流式响应都遵守这个契约。

已是字典的参数直接使用；合法 JSON 字符串解析一次。无法解析、非对象参数或不完整工具调用，沿用现有 `ProtocolResponseError`，不进入工具执行。

不把普通文本 JSON 转成工具调用，不自动补括号、尾逗号、字段或参数值。本次先保证错误归属清晰；是否使用后端的严格 schema 约束，需要依据实际服务能力单独核实，不能在计划中声称已具备。

### 执行层与 Todo 工具

执行层根据统一工具块查找处理函数，并通过现有 Hook 执行、记录结果，不自行解析 JSON。

保持现有普通同步工具按返回顺序执行、后台工具派发后先返回启动结果的规则。本次不增加依赖推断、自动拆批或并发调度，也不替模型生成后续工具参数。

`todo_write` 检查 `todos` 是列表，每项是对象，`content` 是字符串，`status` 属于 `pending / in_progress / completed`。检查通过后替换整份列表、发布 `todo_updated` 并保存检查点；检查失败返回工具错误，保持原列表。

这里检查的是接口数据，不是任务事实。“运行测试”被模型标记为 completed，不代表工具检查已经证明测试通过。

### 两种失败的边界

| 情况 | 失败位置 | 处理方式 |
| --- | --- | --- |
| 工具参数 JSON 不完整、顶层不是对象，或工具调用本身未完整返回 | Provider 协议解析 | 沿用 ProtocolResponseError；该响应整批调用不执行，反馈错误并结束本轮，不自动重试该协议响应 |
| 工具名和参数对象已解析成功，但 Todo 列表缺字段、类型或状态不符合约定 | Todo 工具参数检查 | 返回具体错误作为该调用的 tool_result；该次更新不改变当前列表，不发布成功更新事件；模型收到结果后决定后续调用 |

协议解析失败的例子是参数字符串 `{"todos":`。它无法成为完整参数对象，尚未进入 Todo 工具。这类失败也可能来自响应截断或服务返回异常，不直接认定模型选择工具的行为错误。

Todo 参数检查失败的例子：

```json
{"todos": [{"content": "运行测试"}]}
```

这段 JSON 可以解析，调用 `todo_write` 本身也可以合理，但项目缺少 status，因此无法接受这次更新。

Todo 参数检查失败仅影响该次更新。若同批先有一次合法更新，再有一次非法更新，保留前一次合法更新；其他工具已经产生的结果和副作用也保留，不回滚整批。

本次保持 Todo 错误返回 `Error: ...` 字符串的接口，不新建通用错误对象，不重做工具生命周期状态或 is_error 协议。成功摘要只在参数检查及列表更新完成后返回。

### Todo 工具的简短返回

`todo_write` 成功更新列表后，从本次接受的列表统计总数及三种状态的数量，并通过现有 `tool_result` 返回给模型。例如：

```text
已更新 3 项待办：完成 1 项，进行中 1 项，待处理 1 项。
```

这些数量描述模型提交的清单状态，不是对任务完成事实的验证。Todo 工具只知道自身更新是否成功，不查询其他工具的执行情况，也不将工具调用与 Todo 项自动绑定。统计仅在本次更新时计算，不维护跨回合计数器。

工具执行结果和 Todo 状态更新是两个独立动作。例如：模型先提交“运行测试，in_progress”，随后调用 `bash` 执行测试；执行器把测试结果回填给模型；模型据此决定是否再次调用 `todo_write`，将该项改为 completed。一个 Todo 项可以需要多次工具调用，单次工具成功不自动完成该项。

空列表也是合法更新，返回总数及各状态均为零。参数检查失败时返回具体错误，不输出成功更新摘要。

返回内容只包含更新结果与状态统计，不追加“请继续跟踪进度”“请更新 Todo”或“必须调用验证 agent”等执行要求。前端继续根据 `todo_updated` 展示列表，无需解析这个返回字符串。

### 会话与前端

会话继续保存和恢复 Todo 内容。CLI/TUI 消费现有事件展示模型提交的状态。运行时不追加 Todo 提醒消息，不新增提醒事件，也不新增 `TodoTracker`。

不修改系统提示词，不扩写 Todo 工具描述。

## 范围限制与实际影响

去掉提醒后，模型可能忘记更新 Todo；系统保留模型最后明确提交的状态，不自动纠正。

本次不建设新的通用 Tool 框架，不改变 Task、子 agent、worktree、goal 和权限路线，不新增依赖。字符串形式的 Todo 参数将明确报错，工具只维护当前列表接口。

原生工具调用解决的是明确的执行入口。要进一步减少模型产生格式错误，应核实实际 API 的 schema 约束能力；本次不通过猜测修复 JSON 来声称解决这一问题。
