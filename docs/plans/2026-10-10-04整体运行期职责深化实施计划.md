### 1.1 审查结论的更正

规划期逐条复核审查报告，更正两处结论：

**子 agent 加锁顺序一致，不存在反向嵌套。** `subagent.py:224-234`（`apply_plan_response`）与 `subagent.py:423-433`（`spawn_subagent`）都是 `tasks.task_lock` 再 `subagent_lock`；`subagent_protocol.py` 内部不加锁；`submit_plan`（`:506`）、`run_review_plan`（`:577`）同序。C3 的问题不是顺序矛盾，而是顺序不被任何单一模块强制，且调用方需自行持有五个锁与全局。

**C5 原定的两个重复点都不成立。** 委派正文：workflow 在 `workflow_runtime.py:300-305` 组装 `Step label` 与 schema JSON 指令，交互侧在 `subagent_session.py:142-149` 组装 `[Current work]` 上下文、并在 `:203-204` 把正文放进系统提示，格式、内容与去向都不同。token 口径：`Budget._spent` 是单整数（`workflow_runtime.py:441-466`）、`_MeteredClient.usage` 是 `{"tokens","model_calls"}` 字典（`subagent_session.py:44-52`）、`LeadTurn.accept_response` 上报的是 usage 对象（`lead_turn.py:70-75`），单位与用途都不同。硬收成一个来源等于换位置。详见第 9 节。

## 5. C1：会话切换拥有者契约

已实施（提交 `93e5fa9`）。现状与结果：

- 新增 `runtime/session_switch.py`，interface 只有 `switch(target)`，返回 `{"text", "workdir", "saved"}`。
- `InteractiveRuntime` 的 `_prepare_resume`、`_resume`、`_activate_resume` 删除，`/resume` 改为委托。
- 三段保护结构收进实现：服务已停且激活失败时回滚服务；`session_changed` 恒发布；后处理失败时置暂停标志并包成 `SessionError`。
- `SessionStore` 文件格式与 `InteractiveSession.activate` 行为未变；`tasks.validate_lead_context` 仍是恢复前校验入口。

**收益门的实际达成度（如实记录）**：切换 module 注入 11 个依赖；六项归属写入直接在实现内（`core.WORKDIR`、`store.workdir`、`mcp_clients`、`LeadContext.activate`、`activate_lead_assignment`、`session.activate`），`goal` 替换经注入的 `read_goal`/`replace_goal` 回调，`_usage` 重置与 `_generation` 递增经 `after_activate` 回调。后三者保留在 seam 上的理由：`goal` 与运行时计数由运行时的线程与生命周期拥有，搬入切换 module 会使依赖方向反转（切换模块反过来持有运行时状态），与 C2 的目标冲突。

调用方收益门已达成：调用方从「按序执行 7 步并在失败时手工回滚」变为「调 `switch(target)` 并提供一次状态刷新回调」。此残留是本计划第 12 节列的失败条件之一，此处显式认下，不再扩大改动。

## 9. C5：已取消

原计划 C5 要求收拢两个「重复点」。规划期逐条复核后，两个都不成立：

1. **委派正文组装没有重复。** workflow 侧（`workflow_runtime.py:300-305`）组装的是 `Step label: <label>` 与一段 JSON schema 指令；交互侧（`subagent_session.py:142-149`）组装的是当前 Task 与工作目录上下文，`_request`（`:203-204`）再把正文放进系统提示的 `[Current delegation]` 段。格式、内容、去向三者都不同，硬合并只会产出一个「interface 与 implementation 一样复杂」的浅 helper。
2. **token 口径不是同一件事。** `Budget._spent` 是单整数并驱动预算上限（`workflow_runtime.py:441-466`）；`_MeteredClient.usage` 是 `{"tokens", "model_calls"}` 字典供子 agent 上报（`subagent_session.py:44-52`）；`LeadTurn.accept_response` 上报的是原始 usage 对象（`lead_turn.py:70-75`）。三者单位与消费方都不同，统一等于换位置。

复核同时发现一处真实的重复，但收益不足：`operation_status("model", "请求模型", ...)` 在三个模块共六处独立重复——`lead_turn.py:80`、`subagent_session.py:200/208/211`、`host.py:183/203`，各自维护「何种结果算 failed/stopped/discarded」的映射与同一句错误信息拼接。这属于报告级别的重复，稳定且已被现有测试覆盖，收益低于 C1–C4（省掉的是三处汇报代码，而非消除一条需要理解的规则）。

**决定：取消 C5**，进入 C1–C4 的范围外。命中本计划原第 9 节的失败条件（「收益门不达则收缩或取消」）。若将来该六处汇报开始漂移或需要加入新的状态映射，再单独立项。

| --- | --- |
